# BusinessEntity — установка через BotFactory в существующий User Hub

## Назначение и параметры

Сценарий предназначен для `client001` и сервера `192.168.55.15`.
Согласованные параметры: BusinessEntity `https://192.168.55.15:7070`, первый
администратор — существующий пользователь Hub `admin`.

User Hub проверяется по HTTPS-паспорту схемы 1 и ID
`15f176e4-dbe7-44b6-a3f2-9d66c73ba2b7`, а также локальному описанию и Docker labels.
Используется принятый Hub на `https://192.168.55.15:9440`.

Создаётся отдельный Compose-проект `businessentity` в `/srv/businessentity`:
приложение, PostgreSQL и web logger, собственная сеть и том БД. Наружу открывается
только HTTPS7070. Kestrel непосредственно обслуживает TLS, поэтому схема OIDC
callback не зависит от доверия forwarded headers. CA добавляется в образ приложения.

В существующем Authentik создаются отдельные application/provider, использующие
его действующие flows и signing key. Пользователь `admin` связывается по UUID
при `sub_mode=user_uuid`; пароль не читается и не сбрасывается. Первый успешный
OIDC-вход назначает этому пользователю локальные права администратора BE.

Новые Hub/Authentik в этом сценарии не устанавливаются. При несовпадении паспорта,
ошибке HTTPS, отсутствии Hub, занятом порте или неподходящем admin операция
прекращается. Ветка дополнительного Hub остаётся будущим расширением.

## Пункты меню ALBERT

1. `BUSINESSENTITY-INSPECT-USERHUB-V1` — «BusinessEntity — проверить Hub и установку на 7070».
   Проверяет паспорт/readiness, выбранного пользователя, сертификат, Compose и
   свободный порт. Сохраняет публичный план с SHA256 исходников и кодом подтверждения.
2. `BUSINESSENTITY-INSTALL-USERHUB-V1` — «BusinessEntity — установить на 7070 в существующий User Hub».
   Выбор этого пункта после просмотра проверки подтверждает использование найденного
   Hub. Нужен успешный `preflight.json` для того же пакета. На сервере план
   вычисляется заново; изменённые параметры/UUID администратора отклоняются.
3. `BUSINESSENTITY-STATUS-USERHUB-V1` — состояние собственной установки: фаза,
   контейнеры, последние журналы и HTTPS. Результат — `status.json`; пароли из
   приватного состояния редактируются перед возвратом журналов. Клиентский сценарий:
   `ac673a84-64ba-4445-8c09-7820a63431a5`.

Общий клиентский сценарий: `4f38535d-faaa-4904-a658-44dd1565c85d`.
Транспорт: штатный `GEO-RCMD_D9DQN` → client001 → SSH/SFTP с проверкой ключа сервера.
SSH и VPN credentials используются из существующих локальных хранилищ клиента.
Сценарии User Hub не редактируются и не запускаются для переустановки Хаба.

## Исходники и подготовка пакета

```bash
python3 Deployment/botfactory/build_payload.py
python3 Deployment/botfactory/build_scenarios.py
python3 -m unittest discover -s Deployment/botfactory -p 'test_*.py'
```

Пакет фиксирует **текущее содержимое рабочей копии**, включая незакоммиченный
AUTH/API-код. Git HEAD в manifest служит исходной точкой, а не утверждением,
что весь пакет закоммичен. Точный состав задают SHA256 архива и каждого файла.
Упаковка берёт реальные исходники трёх каталогов, поскольку существующий
`.gitignore` скрывает часть исходников BackupRestoreMiniApp. Сборочные каталоги,
локальные env, ключи, сертификаты, runtime identity-файлы и development config исключены.

Пакет: `artifacts/botfactory-businessentity` (игнорируется Git).
После изменения установщика, request или исходников нужно заново подготовить пакет,
сгенерировать определения и опубликовать **оба клиентских и три серверных сценария**
через собственную API-сессию BotFactory с актуальными base_version. Они закрепляют
SHA256 manifest; подмена файлов без обновления определений отклоняется.

`install-request.example.json` содержит согласованную конфигурацию этой установки.
Изменение порта или целевого сервера требует изменения явных проверок runner,
генерации нового пакета и повторной проверки. Это адресный сценарий первой установки,
а не универсальный установщик любого сервера.

## Состояние и повтор

- `/srv/businessentity/installation.json` — приватное состояние, ID и секреты;
  файл `0600`, корневой каталог `0700`. В публичный отчёт секреты не входят.
- `compose.json` и `identity.initial.json` создаются приватно на сервере.
- Хранилище, DataProtection keys и БД принадлежат новому Compose-проекту.
- Идентичный повтор сохраняет ID/секреты и переиспользует только собственные
  OIDC-объекты. Завершённая установка проходит проверку и не пересоздаётся.
- Другой source SHA на существующей установке отклоняется как
  `EXPLICIT_UPDATE_REQUIRED`. Обновление схемы и откат старой БД требуют отдельного сценария.
- При ошибке собственные данные и регистрации сохраняются для диагностики и
  идентичного повтора. Автоматического удаления volumes, пользователей или провайдера нет.
- При обрыве SSH сначала проверить состояние своей операции/процесса и файл
  установки. Блокировка на сервере запрещает параллельное выполнение install.

Успешный результат install означает доступность HTTPS и корректное OIDC
перенаправление с PKCE и точным callback. Поле `browserLoginVerified=false` явно
указывает, что настоящий вход, назначение прав и работа интерфейса ещё требуют
браузерной приёмки. Установщик не получает пароль `admin`.

В этом пакете `ApiTokenProfiles=[]`: вход пользователя подключён к общему Hub;
машинные клиенты и допуски внешнего API настраиваются отдельно.

## Артефакты проверки

Публичный план: `artifacts/botfactory-businessentity/preflight.json`.
Результат установки: `artifacts/botfactory-businessentity/installation-result.json`.
Статус фактических прогонов фиксируется в `verification.md` рядом с этим файлом.
Подготовка сценария и успешная локальная сборка не означают установки на сервере.
