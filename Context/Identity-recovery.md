# Восстановление доступа к провайдеру

Команда `identity-recover <ProviderId> <Revision>` предназначена для оператора,
имеющего доступ к серверу и конфигурации установки. Она возвращает известную
сохранённую ревизию профиля, увеличивает AuthEpoch и сохраняет запись
`OperatorRecovery` вместе с исходом операции в SQL. Старые сессии не оживают.
Анонимного HTTP endpoint восстановления нет.

## Условия

- Использовать ту же БД, canonical storage и каталог DataProtection keys.
- Остановить сервер данной установки. Поддерживается один процесс приложения
  на БД; session advisory lock блокирует вторую копию сервера или recovery.
- Целевой профиль уже сохранён; его discovery/JWKS должны быть доступны.
- Уже существует включённая привязка включённого локального Human с GlobalAdmin
  к цели. Временный пароль должен быть сменён. При наличии management adapter
  проверяется соответствующий внешний аккаунт и точный subject.
- Новая пустая БД не подходит. Команда не создаёт администратора, не связывает
  пользователей по имени и не меняет внешние пароли.

## Docker Compose

Работать из корня нужной установки с её `.env`. Выбрать сохранённые ProviderId
и Revision из операторской записи конфигурации; произвольный URL не принимается.

```powershell
docker compose stop business-entity
docker compose run --rm --no-deps --entrypoint dotnet business-entity BusinessEntity.dll identity-recover <ProviderId> <Revision>
docker compose up -d --no-build --no-deps business-entity
```

Выполнять следующий шаг после завершения предыдущего. Убедиться в exit 0 recovery
и сообщении о выбранных профиле/ревизии/epoch; затем проверить новый интерактивный
вход. Вход через старый issuer не заменяет проверку целевого. При ошибке команда
не делает fallback. Перед повтором после потери результата проверить committed
выбор и журнал; повторная успешная recovery увеличит epoch ещё раз.

Команда не удаляет БД, файлы, Docker volumes или созданные у провайдера аккаунты.
В журнал и вывод не попадают временные пароли или значения секретов.

Фактические результаты проверки фиксируются отдельно в
[журнале раскатки](Tasks/TASK_AUTH_API_execution-log.md). Наличие этой инструкции
само по себе не означает завершение приёмки recovery или AUTH_001.
