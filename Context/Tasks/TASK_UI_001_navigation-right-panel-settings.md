## 4. UI-02. Правая панель как расширяемый host модулей

### 4.1. Внешний вид

- На прежнем месте правой колонки — полоса вкладок с фоновой заливкой по образцу
  Geo4Web, ниже содержимое выбранной вкладки. Высота полосы и типографика общие
  для этого host-а, цвета берутся из темы.
- Удалить заголовок «Панель настроек и виджетов» и постоянный виджет «Информация».
  Сообщения больше не имеют второго внешнего widget-заголовка внутри вкладки.
- В начальном составе ровно одна вкладка **«Сообщения»**, открыта по умолчанию,
  не закрывается. При пустом журнале — «Сообщений пока нет».
- Не добавлять «Контекст», заглушку второй вкладки, часы и другие виджеты.
- Не добавлять splitter, drag-handle, resize-поведение или настройку ширины.
  Сохранить существующую ширину и breakpoint-правила BE. Колонка не должна
  вызывать горизонтальный overflow; длинные сообщения имеют перенос и прокрутку.
- Сворачивание Geo4Web и его localStorage ширины в данный пакет не переносить:
  пользователь запросил вкладки и отдельно исключил сплиттер.

### 4.2. Владельцы и runtime

Сделать `RightPanelMiniApp` владельцем панели как UI-host-а. Его единственный
WindowSingleton-модуль размещается в существующем shell-slot `RightPanel`.
Shell знает имя места, но не перечисляет прикладные вкладки.

Механика auxiliary tabs находится в общей `Infrastructure\Modularity` и
использует существующий `ModuleCatalog`/`WindowModularityManager`. Не заводить
второй manager, вторую шину или отдельный каталог бизнес-сущностей для вкладок.
Вкладка — runtime-модуль, а не сохраняемый `BusinessEntity`.

Расширить декларацию модуля ровно необходимыми сведениями: размещение auxiliary
tab, идентификатор области, ComponentKey, порядок, заголовок, право доступа,
политика экземпляра и возможность закрытия. У `UserMessagesMiniApp` его
`UserMessages.Panel` объявляет вкладку для правой области; панель не импортирует
`UserMessagesMiniApp.Internal` и не создаёт его компонент напрямую.

Обязательный контракт host-а:

1. Получать вкладки из деклараций и runtime snapshot manager-а, фильтровать по
   области, LogicalWindowId и действующим правам.
2. Создавать один экземпляр WindowSingleton на окно. Re-render, prerender,
   повторное создание host-а и reconnect не создают повторные вкладки/подписки.
3. Стабильный порядок: Order, затем стабильный идентификатор при равенстве.
4. Selected tab — состояние своего окна. Переключение вспомогательной вкладки
   не меняет центральную страницу, её активный module/master и SaveContext.
5. Смена вкладки не уничтожает её рабочее состояние. После снятия модуля
   освобождать подписки и не применять поздние callbacks.
6. Обрабатывать неизвестный ComponentKey явной диагностикой.
7. Поддержать tablist/tab/tabpanel, aria-selected, фокус и клавиатурное
   переключение; при удалении выбранной вкладки выбрать первую доступную.

Расширяемость проверить тестовой второй декларацией: она появляется без правки
`MainLayout`, `RightPanelMiniApp` и кода «Сообщений». Тестовый модуль в рабочую
поставку не включать. Полный перенос Geo4 owner-bound workspace/move/float
механики не нужен: в BE нет соответствующей центральной вкладочной модели.

### 4.3. Явное изменение прежней нормы

Текущие `Context\index.md`, `Policy\MiniApps\modularity-policy.md` и решения

## 5. UI-03. Уведомления через общую шину

Использовать и расширять существующий `UserMessagesMiniApp`. Он уже хранит
ограниченный журнал, фильтрует `UserId + LogicalWindowId` и устраняет повтор
CorrelationId. Это рабочая основа, а не повод создавать новый toast-service.

### 5.1. Какие сообщения переносить

Перенести в правую вкладку завершения операций, предупреждения и ошибки из:

- общих и системных параметров;
- администрирования пространств;
- пользователей, ролей, групп, memberships, назначений прав;
- профиля, настройки identity providers и интеграций API;
- новых страниц тем и компоновки;
- остальных живых страниц BE, где операция пока выводит отдельный status/alert.

Перед правками составить короткий реестр фактических публикаций/inline status
по живому коду. Уже переведённый поток `UsersAdministration` не должен получить
вторую публикацию. После удаления служебных страниц их сообщения переносить некуда.

Не превращать в уведомления весь текст интерфейса. Подписи, подсказки полей,
списки данных, пустые состояния, индикаторы загрузки и требующие действия
диалоги остаются на месте. Field validation остаётся у поля; итоговая ошибка
неуспешного Save попадает в журнал один раз. Подтверждение удаления не заменяется
неинтерактивной карточкой. Однократно показываемые credentials остаются в
адресном защищённом UI выдачи и **не попадают в журнал**.

### 5.2. Доставка и адресация

- Между миниаппами — `PostUserMessage` по единственной шине. Адрес берётся из
  серверного `BusRequestScope`/проверенного пользователя, не из браузерного DTO.
- При необходимости добавить в контракт `SourceMiniAppId` с единым обновлением
  отправителей. Источник пригоден для диагностики, но не даёт дополнительных прав.
- Одна операция имеет устойчивую корреляцию; повтор обработки одного исхода
  не создаёт ещё одну карточку. Success публикуется после подтверждённого Save,
  Unknown не выдаётся за успех или откат.
- Назначить один уровень, ответственный за пользовательскую публикацию ошибки.
  Поймавший её вышестоящий слой не публикует ту же ошибку повторно.
- Сборщик и подписки живут в scope окна и готовы до операций центральной
  страницы; временное отсутствие/скрытие UI вкладки не теряет сообщения.
- Обычная навигация между страницами не очищает журнал. Очистка относится только
  к журналу текущего пользователя и окна. Лимит 50 сохранить; постоянное хранение
  сообщений, безадресные broadcast и лимит Geo4 в 200 записей здесь не требуются.
- HTTP flash-доставка после полного перехода сохраняет действующую одноразовую
  проверку адресата. Не расширять её до общей очереди для всех пользователей.
- UI callback выполняется через owning renderer и проверяет завершение lifetime.
  Закрытый circuit не получает поздний StateHasChanged.

Уровни Info/Success/Warning/Error и различимые заголовок, текст, время должны
читаться без зависимости только от цвета. Технический стек остаётся в ILogger;
пароли, токены, secret references с раскрытыми значениями и connection strings
не включаются в пользовательские карточки.

Администрирование уже является миниаппом навигации. Предметные уведомления
публикуют реальные владельцы операций: SysParameters, Spaces, User и другие.
Не переносить их бизнес-логику в `AdministrationMiniApp` ради общего оформления.

## 6. UI-04. Разделы и жизненный цикл настроек

### 6.1. Структура центра

Перестроить существующий административный центр по визуальной схеме Geo4Web:
заголовок, вертикальный список разделов слева, рабочее содержимое справа,
последовательное оформление свойств и действий. Сохранить BE-названия и поля.

В левом списке должны быть все действующие разделы, разрешённые пользователю:
«Общее», «Параметры системы», «Пространства», «Пользователи», «Провайдеры
идентификации», «Интеграции API»; добавить «Темы оформления» и «Компоновка».
Вложенные разделы пользователей и их операции не удалять.

Сохранить существующие deep links `/administration/...`, историю браузера,
выбранный раздел после refresh и серверные guards. Новые страницы:
`/administration/appearance/themes` и `/administration/appearance/layouts`.
Шестерёнка ведёт в существующий центр; это не поручение выдавать административный
доступ всем пользователям. Текущие `Administration`, `GlobalAdmin`, `AdminSpace`
сохраняют смысл. Новые персональные разделы доступны допущенным в этот центр
пользователям и изменяют только их собственные настройки.

### 6.2. Расширение страницами владельцев

Адаптировать подход `IApplicationSettingsPageProvider`: стабильные PageId,
Title, Order, route, permission, ComponentKey и lifecycle draft. Сама регистрация
UI выполняется через реестр компонентов BE. В bus-сообщениях не передавать
`Type`, Razor, delegate, IServiceProvider и экземпляры внутренних сервисов.

Каждый миниапп регистрирует свой раздел и сохраняет свой draft. Общий центр
только строит навигацию и организует жизненный цикл. Он не копирует формы User
и SysParameters внутрь себя и не обращается к их Internal. Не использовать
пользовательский AppSingleton из Geo4 буквально: runtime UI и draft BE отделены
по окнам, статические объявления могут оставаться общими.

### 6.3. Сохранение, отмена и явные действия

Для разделов с редактируемыми настройками повторить семантику Geo4:

- открытие создаёт draft от применённого состояния;
- переход между разделами одного центра не применяет и не теряет draft;
- «Применить» сохраняет изменённые drafts настроек и оставляет центр открытым;
- «OK» делает то же и после успеха возвращает на безопасную исходную страницу
  BE; если исходной страницы нет, на `/`;
- «Отмена» отбрасывает ещё не применённые правки и возвращает визуальное состояние
  к последнему успешному Apply; уже выполненные Apply не откатываются;
- обычный уход из центра/закрытие окна использует существующий navigation guard
  Save/Discard/Cancel. Не вводить второй независимый вопрос поверх него.

При этом различать **настройки-draft** и **операционные формы**. Создание/удаление
пользователей, memberships, смена IdP, выдача credential, отзыв API grant,
reseed и другие самостоятельные операции выполняются только своей явной
командой. Общие Apply/OK никогда не запускают их. Их текущие подтверждения,
права, одноразовые результаты и транзакционные границы сохраняются.

Рабочие наборы системных/пользовательских данных используют имеющиеся
SaveContext, validators и typed owner commands. Общий Apply координирует только
зарегистрированные участники настроек; не выдаёт несколько отдельных SQL/local
операций за одну атомарную транзакцию. При частичном отказе центр остаётся открыт:
успешные участники имеют новую baseline, оставшиеся drafts сохраняются, журнал
точно сообщает результат. Не очищать dirty и не закрывать окно при Unknown.

Существующий API системных параметров продолжает работать через те же правила.
Перекомпоновка формы не меняет сохранённые значения, диапазоны и семантику API.
Текст о внутреннем хранении в `SysParameters` не нужен в пользовательской форме;
технические объяснения остаются в документации.

## 7. UI-05. Темы оформления и компоновка

Следующие решения адаптируют показанный образец к BE. Они являются техническим
контрактом этого пакета, а не утверждением, что каждое поле было проговорено в видео.

### 7.1. Темы и область хранения

Создать `ThemeManagerMiniApp` с typed-моделью, валидацией, CSS mapper, browser store
и редактором по структуре Geo4Web. В этом срезе нужны встроенная неизменяемая
`BusinessEntity Light` и локальные пользовательские темы браузера.

Geo4 project themes не превращать автоматически в темы Space: такого требования
нет. Не создавать для тем новые бизнес-сущности, связи пространств или БД.
Каталог, активная тема и палитра хранятся в localStorage данного origin под
namespace стабильного локального UserId; тема другого пользователя не подхватывается.
У анонимного посетителя — встроенная тема. UI-доступ к редактору определён §6.1.

Нужные команды: новая тема, дублирование, переименование, удаление своей темы,
импорт, экспорт, предпросмотр, сохранение темы и применение. Встроенную тему
можно просмотреть и дублировать, но нельзя изменить или удалить. Импорт/копия
создают новую идентичность и свободное имя. Удаление активной локальной темы
явно возвращает встроенную и корректно обновляет выбранный каталог.

Редактор использует единый draft, компактные команды и группы параметров.
Перенести действующие для BE части образца:

| Раздел | Содержимое |
|---|---|
| Общий | Основные роли цветов, фон модуля, выбор и доступные в BE полосы/вкладки, читаемый foreground |
| Скроллбары | Цвета и состояния прозрачности применяемых scroll surfaces |
| Таблицы | Каталог стилей и активный стиль для общих административных таблиц; не менять предметный HTML-контент документов |
| Сообщения | Оформление четырёх уровней и preview; body, акцент, рамка, тень, ширина полосы; дизайны Geo4: AccentBarLeft/Right, StatusIcon/Right, SolidAccentBarLeft/Right |

Параметры с отсутствующим потребителем не показывать. Не переносить Корреляцию,
линейки, свойства кривых, рабочие вкладки Geo4 и неработающие splitter-настройки.
В частности, разделитель справа не появляется от включения темы.

Сохранить подход color picker: HEX, визуальный выбор, предпросмотр, подтверждение
выбора и пользовательская палитра 16 слотов. Смена вкладки редактора не сохраняет
тему автоматически. Предпросмотр касается только текущего окна. Сохранение темы
и выбор активной темы — явные операции; Cancel после preview восстанавливает
последнюю применённую тему, не удаляя уже явно сохранённые элементы каталога.

### 7.2. Контракт формата и применения

- Формат BE: собственный versioned JSON, marker `BusinessEntityTheme`, схема 1,
  расширение `.betheme`. Не объявлять совместимость с `.geo4theme` schema 19.
- Лимит импорта 256 KiB; проверять структуру, обязательные поля, enum, цвета,
  числа и ссылки до изменения каталога. Неизвестная версия/поле или повреждение
  дают явную ошибку, а не частично созданную тему.
- Полная запись browser catalog атомарна через одну операцию setItem. Ошибка
  quota/storage не меняет подтверждённое in-memory состояние и показывается в журнале.
- Документированный старт при отсутствии каталога — встроенная тема. При
  повреждённом/несовместимом каталоге оболочка остаётся на встроенной теме и
  выдаёт одно предупреждение/ошибку; исходный payload не перезаписывать молча.
  Это явный ограниченный recovery-контракт, а не скрытая миграция.
- Scoped state принадлежит circuit. Постоянный namespace не означает общей
  mutable темы singleton. Preview не рассылается в чужие окна и пользователям.
- Один mapper вычисляет производные семантические роли; компоненты потребляют
  `--be-*` переменные. Раннее применение перед Blazor и обычное применение
  используют один allowlist и согласованные правила, без вспышки чужой темы.
- Не принимать произвольный CSS/JS, внешние URL и исполняемый HTML в теме.
  Не менять цвета пользовательского rich-text контента как побочный эффект темы UI.
- Проверить темы на оболочке, панели сообщений, новом центре настроек, кнопках,
  таблицах и оставшихся страницах. Не объявлять тему реализованной по одному picker.

### 7.3. Компоновка

Повторить текущий первый срез Geo4: страница «Компоновка» с единственным
неизменяемым вариантом `standard` («Стандартная»), его описанием и участием в
Apply/Cancel. Это фактическая компоновка BE: прежняя левая полоса и дерево,
центральная страница, правая панель сообщений без resize.

Выбор — персональное техническое свойство UserMiniApp; использовать его
публичный connector и штатный writer/SaveContext, без прямого EF из UI.
Новый тип свойства и metadata объявить в User, не заимствовать числовой код 302
из Geo4 без проверки. Отсутствие свойства означает `standard`; неизвестное
сохранённое значение даёт наблюдаемый отказ и оставляет работающую standard
компоновку, не затирая исходное свойство.

Не создавать конструктор layouts, дополнительные схемы, переключатель в шапке,
project persistence или скрытые галочки для изменения ширины панели.


Реальные PostgreSQL-тесты требуют отдельного `BE_TEST_POSTGRES`. Рабочую БД для

Эти числа — база сравнения, а не приёмка новой реализации.

- деклараций вкладок, уникальности, late registration, окно/права/lifetime;

1. Что выполнено по UI-01…UI-05, конкретные отличия от образца Geo4 и их основания.
2. Состав изменённых контрактов, политики, реестры и журнал этапов.
3. Результаты сборки/тестов с разделением passed, failed и skipped.
4. Фактические результаты A01–A18, включая ограничения проверки.
5. Если была поставка — точную версию/commit/образ, адрес, результат проверки
   сохранности данных и готовность отката. Если поставки не было — явно указать это.

Задача не считается завершённой по одному обновлённому макету: удалённые
маршруты действительно отсутствуют, вкладки расширяются декларациями, сообщения
проходят по шине, а настройки и темы реально применяются и сохраняются.
