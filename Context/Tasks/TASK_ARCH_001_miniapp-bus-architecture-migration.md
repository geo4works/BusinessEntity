## 1. Назначение и объём

### 1.1. Цель

Миниапп изолирует предметную функциональность: состояние, сценарии, сообщения
и интерфейс своего домена. Общие модели и алгоритмы движка находятся в Core
и используются всеми миниаппами без копирования. Межминиаппное взаимодействие
идёт через одну типизированную шину.

Сохранение относится к рабочему экземпляру миниаппа и может включать много
связанных сущностей. Миниапп отправляет единый пакет изменений в DataProvider,
который обеспечивает атомарное применение и постоянное хранение.

### 1.2. Целевая формула

```text
Core                 = общая модель и сервисы движка.
Infrastructure       = шина, клиент запросов, модульность, сохранение, логирование.
Миниапп              = изолированный домен функциональности.
Рабочий экземпляр    = состояние миниаппа в определённом окне и контексте.
Контекст сохранения  = весь связанный набор правок рабочего экземпляра миниаппа.
UI-модуль            = представление или фоновая часть; создаётся инфраструктурой.
Host-service         = только декларации модулей и команд.
Оболочка             = геометрия и именованные места.
Страница             = URL, guard доступа и хост модуля.
Шина                 = один IMessageBus singleton на приложение.
DataProvider         = применение транзакций, хранилище и кэш графа.
Тип сущности         = правила версий, состава истории и срока хранения.
```

### 1.3. Пункты объёма

| Пункт | Содержание | Этапы |
|---|---|---|
| Шина | Общий клиент, ошибки, адресация, жизненный цикл подписок | 1 |
| Хранилище | Единственный путь чтения/записи, транзакции миниаппа, история статей | 2 |
| Кэш | Снимок графа, проекции чтения, согласованность после коммита | 3 |
| Модульность | Декларации, рабочие экземпляры, контексты сохранения | 4 |
| Интерфейс | Именованные места, страницы, меню и кнопки декларациями | 5 |
| Границы | Общий Core и доменная логика миниаппов | 0, 2, 6 |
| Выделение | Адресный протокол master/helper | 7 |
| Сохранённость | Dirty миниаппа, Save/Discard/Cancel, защита навигации | 4, 6, 8 |
| Документация | Политики, реестры, итоговый аудит | 0, 9 |

### 1.4. Вне объёма

- Версия пространства/проекта, общий журнал истории, откат хвоста истории пространства.
- Dirty пространства и глобальная команда сохранения всей установки.
- Лента, внутренние вкладки, WorkspaceTab и TabbedHostArea.
- Автоматическое слияние конкурентных правок и отказ второго сохранения только
  потому, что пользователь начал редактирование старой версии.
- Горизонтальное масштабирование и распределённый кэш.
- Полная универсализация физической схемы чанков, сжатие всех payload и перенос
  проектного формата Geo4. Общая модель чанка в Core допустима без смены всей схемы.
- Конкретные capability toolset-ы: в этапе 9 фиксируется только политика применения.

Транзакции сохранения миниаппа входят в объём. Снятое ранее решение о полном
отказе от таких транзакций больше не действует.

| Id | Решение | Уточнение |
|---|---|---|

| Р-2 | Dirty и Save относятся к рабочему экземпляру миниаппа | Один Save может содержать множество связанных сущностей; он отправляет транзакцию в DataProvider |
| Р-3 | Интерфейс построен на переходах по страницам | Для двух страниц одновременно пользователь открывает второе окно браузера |
| Р-4 | Ленты нет; команды и меню объявляются декларациями | Навигация, тулбар документа, контекстное меню дерева |
| Р-5 | Одна общая шина на всё приложение | Изоляцию пользовательских действий обеспечивает адресация |
| Р-7 | Переход на .NET 9 подтверждён | Обновляются приложение и логгер |
| Р-9 | Первая запись новой статьи создаёт v1 | Далее версию создают изменения контента или названия; публикация выбирает существующую версию |

Слияния и уведомлений нет. Если B был неправ — восстанавливают v2. Пользователь назвал это осознанной полумерой «пока» (2026-10-28) |
| Р-11 | Миниаппы логически изолированы в одном проекте | Отдельная сборка на миниапп не требуется; границы проверяются архитектурными тестами |

| Р-13 | Общий слой Core сохраняется и развивается | BusinessEntityHelper, общие модели, фабрики и движковые сервисы используются повторно |
| Р-14 | Предметные правила принадлежат миниаппу/типу, атомарная запись — DataProvider | Правило не требует переносить политику версий статьи в общий storage-сервис |
| Р-15 | Dirty пространства сейчас не отслеживать | Не вводить индикатор или агрегирующий механизм сохранения пространства |
| Р-16 | Без наследия: обратная совместимость не нужна | Никаких миграций данных, адаптеров старых API, «совместимых» полей, чтения старых форматов и переходных обёрток, переживающих свой пакет работ (§3.11) |
| Р-17 | Коммит и push после каждого этапа | После этапов 0–8 — `CMMTP 3`, после этапа 9 — `CMMTP 2` с итоговым описанием всех этапов в CHANGELOG (§0.2 п. 7–8) |

не увеличивают номер. Опубликованная версия выбирается отдельно от latest.

## 3. Целевая архитектура

### 3.1. Общий слой и границы миниаппов

```text
BusinessEntity/
  Core/
    ...              общие Entity, Data, Chunk, Relation и контракты
    Services/        BusinessEntityHelper, фабрики, операции движка
  Infrastructure/
    Bus/             общий транспорт и клиент запросов
    Modularity/      декларации, реестр UI, жизненный цикл
    Saving/          общая механика dirty и подтверждения сохранения
  MiniApps/<Name>MiniApp/
    Contracts/       публичные сообщения, DTO, коннекторы, декларации
    Connectors/      клиенты шины
    Internal/        доменные сервисы, State, обработчики, рабочие экземпляры
    Components/      представления миниаппа
    Registration/    AddXxxMiniApp и регистрация компонентов
    Facade/          внутреннее связывание и инициализация
```

Core содержит и модели, и общие сервисы, в том числе с DI-зависимостями.
Он не ограничен статическими чистыми функциями. Миниаппы вызывают общие
сервисы напрямую; одинаковые алгоритмы не копируются в разные миниаппы.

BusinessEntityHelper сохраняется как общий сервис движка. Его операции чтения,
работы со связями и подготовки сохранения используют публичный контракт
DataProvider через коннектор и шину. Он не получает репозитории и DbContext.
Общая модель чанка не должна раскрывать EF DTO таблицы чанков.

**К-1. Core не знает конкретных предметных типов.** Общий сервис работает
с графом обобщённо. Всё, что зависит от конкретного типа (создание сущности
и начального payload, правила имени и вложения, состав сохранения), Core получает
через реестр описателей типов. Описатели регистрирует миниапп-владелец типа
в своём `AddXxxMiniApp()`, например `IEntityTypeDescriptor` или эквивалент.
Сейчас `BusinessEntityHelper` содержит 19 прямых ссылок на `Document`,
`RichTextDocument`, `MediaVideo`, `Space`, `Folder`, `SysParameters`
(в том числе `switch` в `CreateEntityForType`). На этапе 6 их нужно вынести
в описатели владельцев, иначе общий Core станет обратной зависимостью
от всех доменов. Из контрактов миниаппов Core может ссылаться только
на публичные `Contracts` DataProvider. Архитектурные тесты разрешают
ровно эту ссылку.

Предметная логика конкретной статьи, публикации, комментариев, пользователей
или мультимедиа находится у владельца домена. Если существующий хелпер смешивает
её с общими алгоритмами, выделяется предметная часть, а общий сервис сохраняется.

Правила границ:

1. Между миниаппами доступны Contracts; Registration вызывается только
   композиционным корнем. Internal, Facade, Components, Storage, Repositories
   чужого миниаппа недоступны по архитектурным правилам.
2. Межминиаппный коннектор обращается только к шине; не инициализирует фасад
   и не использует внутренние кодеки хранения. Свои сервисы миниапп вызывает напрямую.
3. Общий Core/Infrastructure доступен через обычные ссылки и DI.
   Эти слои не должны становиться посредником для доступа к внутренностям миниаппов.
4. Состояние принадлежит определённому владельцу и времени жизни: общее состояние
   сервиса и состояние рабочего экземпляра разделены. Пользовательские правки
   не помещаются в один singleton State всего типа миниаппа.
5. 5–6 зависимостей конструктора требуют рассмотрения декомпозиции;
   7 и более — декомпозиции. Исключение для 6 зависимостей поясняется в коде.
6. В одном проекте модификатор internal не обеспечивает межминиаппную изоляцию.
   Нужны автоматические проверки зависимостей с явными исключениями для Contracts,
   регистрации в композиционном корне и общего слоя.

### 3.2. Одна шина и адресация

```csharp
// Единственный транспорт приложения.
services.AddSingleton<ReactiveUI.IMessageBus, ReactiveUI.MessageBus>();
```

Отдельные шины окна/circuit не создаются. По общей шине проходят декларации,
запросы, ответы, транзакции, события данных, UI-команды, выделение и dirty.

| Идентификатор | Назначение |
|---|---|
| RequestId | Сопоставление конкретного запроса и ответа |
| OperationId | Идентичность операции сохранения при ожидании и повторе |
| UserId | Автор и адресат пользовательского действия, полученный на сервере |
| LogicalWindowId | Runtime-контекст окна браузера; не ID внутренней вкладки |
| ModuleId | Адрес конкретного UI/фонового модуля |
| EditSessionId | Runtime-контекст сохранения рабочего экземпляра миниаппа |
| ContextId | Предметный контекст, например ID статьи |

Имена новых технических контрактов допускается уточнить в реализации,
сохраняя эти смыслы. EditSessionId и ModuleId — разные понятия:
несколько модулей могут использовать один контекст сохранения.

- UI-команды и ответы текущей сессии адресуются окну и нужному экземпляру.
  Для двух окон одного UserId одного UserId недостаточно.
- Обработчик проверяет адрес **до** чтения своего состояния или выполнения работы.
  На адресный Request отвечает ровно один владелец.
- Общие сервисы данных могут быть singleton. Scoped-обработчики допустимы на
  этой же шине при строгой фильтрации адреса и освобождении подписок.
- HTTP-контроллеры и фоновые операции получают явный контекст выполнения:
  они не выбирают случайный текущий circuit. Системный автор задаётся явно.
- UserId не доверяется произвольному вводу браузера. Привязка к текущему
  principal и проверки прав выполняются на сервере. Адресация не заменяет авторизацию.
- События общих данных публикуются всем заинтересованным потребителям;
  подписчик проверяет свой контекст и права перед загрузкой/показом данных.
- Подписки освобождаются при завершении владельца; вызовы компонентов —
  через InvokeAsync. Prerender, повторное создание страницы и reconnect не
  должны создавать два обработчика одного адреса.

Сообщения — типизированные records: Command, Event, Request, Response.
Для сбора деклараций применяются GiveMe… / HereAre… с корреляцией.
Объектные конверты вида `{ string Type; object Payload; }` запрещены.

BusRequestClient обеспечивает подписку до отправки, RequestId, отмену,
таймаут по умолчанию 30 секунд и освобождение ожидания. Все отказы имеют
BusError(Code, Message); коннектор поднимает типизированное исключение.
Законное отсутствие необязательного объекта отделяется от ошибки явно.

Отмена ожидания и таймаут не означают, что транзакция откатилась.
Для сохранения используется OperationId и получение её фактического исхода.
Повтор той же операции не должен создавать ещё одну версию или дублировать записи.

Каждый адресный Request получает результат или типизированный отказ.

к операции. Уже опубликованная ошибка не дублируется на каждом уровне.

и выясняет результат, не объявляя правки сохранёнными или потерянными.

### 3.8. Транзакции и DataProvider

**Транзакция сохранения** — типизированный пакет изменений рабочего
экземпляра миниаппа, который может затрагивать несколько связанных сущностей.
Простая операция над одной сущностью использует тот же механизм.

Пакет содержит OperationId, RequestId, автора, MiniAppId, EditSessionId,
адрес окна/источника и явные наборы изменений сущностей, данных, чанков,
связей, свойств и постоянных файлов по необходимости. Используются типы
Core и публичных контрактов. Нельзя передавать EF-сущности, DbContext,
произвольные SQL-команды или callback для доступа к внутренностям миниаппа.

1. Миниапп/тип проверяет предметные правила и определяет состав изменений.
   Общий Core предоставляет повторно используемый механизм формирования пакета.
2. DataProvider проверяет техническую корректность и целостность пакета,
   применяет связанные изменения БД в одной транзакции.
3. Все входы записи — редакторы, дерево, импорт, комментарии, seed,
   restore и файлы — приводятся к этому пути; обходных репозиторных записей нет.
4. Пересекающиеся сохранения упорядочиваются. Политика типа определяет,
   какие изменения создают версию; DataProvider обеспечивает безопасное
   выделение и применение согласованных номеров как механизма хранения.
   Версии вычисляются от актуального состояния после предыдущей записи.
   Нельзя повторно использовать номер, рассчитанный ранее на клиенте.
5. Оба сохранения принимаются (Р-10). **Каждое сохранение создаёт полную версию
   того состояния, которое сохранил автор**, — без слияния с версиями, появившимися
   после его исходной версии, и без уведомлений о перекрытии. Номер новой версии —
   следующий за последним на момент применения.
   **К-2 (редакция v2.2).** Пакет статьи несёт `BaseVersion` (версию, от которой
   работал редактор) и изменения автора относительно неё: изменённые чанки,
   вставленные, удалённые, порядок, заголовок/manifest. DataProvider строит новую
   версию как **`BaseVersion` + изменения автора**, а не как «последняя версия +
   изменения». Чтобы v3 автора B не подхватила неизменённые им чанки из v2 автора A,
   список чанков версии ссылается на **конкретные строки** чанков
   (`ChunkId` + версия строки), а не выбирается правилом «ближайшая снизу».
   Неизменённые чанки по-прежнему не копируются: новая версия ссылается на те же
   строки, что и её база. Для простого `Document` версия — весь payload автора.
6. После успешного коммита обновляется кэш, публикуются изменения и адресный результат.
   При отказе БД кэш не меняется; потребители не получают ложного события успеха.
7. Повтор OperationId с тем же пакетом возвращает результат ранее выполненной
   операции без повторного применения. Другой пакет с тем же ID — явная ошибка.
   Учёт исходов — технический механизм; это не журнал истории пространства.
   **К-3.** Исход хранится в БД: служебная таблица DataProvider
   (`OperationId` PK, хэш пакета, результат, автор, время). Строка пишется
   **в той же транзакции БД**, что и сами изменения. Только так ответ на
   «таймаут, но запись прошла» достоверен и после рестарта процесса.
   Учёт в памяти недостаточен. Старые строки вычищаются по сроку
   (по умолчанию 7 дней, настройка).
8. Только DataProvider публикует BusinessEntityChanged /
   BusinessEntityRelationChanged и итог применения транзакции.
9. Репозитории, EF DTO и DbContext — внутренности DataProvider.
   Собственные служебные таблицы пользователей/ролей UserMiniApp сохраняются
   как явно обозначенное исключение исходного ТЗ; они не дают права напрямую
   менять BusinessEntities и другие таблицы бизнес-графа.
10. Файлы rich-text, видео и их постоянные метаданные записывает DataProvider.
    Временные файлы подготовки/загрузки и выходной архив бэкапа могут принадлежать
    своему сервису; они не являются обходом записи в каноническое хранилище.

Транзакция БД сама по себе не охватывает файловую систему. Реализация должна
сначала подготовить новые неизменяемые файлы, обеспечить их наличие до публикации
ссылок в БД, а при отказе и рестарте восстановить согласованное состояние.
Удаление старых файлов выполняется после коммита с учётом всех сохранённых версий.
Нужны тесты сбоя записи файла, сбоя коммита и восстановления после прерывания.
Нельзя обещать атомарность файлов только наличием BeginTransaction в EF.

### 3.9. Версии и история статей

- Первое сохранение новой статьи создаёт v1.
- Новая версия создаётся при фактическом изменении контента или названия.
  Импорт, меняющий контент, проходит то же правило.
- Публикация только выбирает существующую версию и не увеличивает номер.
  Описание версии меняется без новой версии; no-op Save её также не создаёт.
- **К-4. Указатель публикации хранится вне версионируемого payload.** Сейчас
  `PublishedVersion` — поле манифеста (`Core/DomainEntities/Document.cs`,
  `RichTextDocument.cs`) и при публикации правится в последней строке истории
  на месте (`UpdateDataInPlaceAsync`). Новый механизм: неверсионируемое
  свойство сущности (например `BusinessEntityProperties` с типом
  «опубликованная версия») или колонка карточки. Тогда публикация не трогает
  ни одну строку истории, а копирование манифеста в следующую версию не
  переносит устаревший указатель. Описание версии остаётся метаданными строки
  версии (это не содержимое).
- Состав истории и срок хранения задаёт владелец типа. DataProvider не вводит
  общий номер версии пространства и не определяет бизнес-правила публикации.
- Заголовок/manifest и изменения чанков сохраняются одной транзакцией.
  Строка изменённого чанка получает номер новой версии статьи; неизменённые чанки
  повторно не копируются.
- Каждая версия хранит свой список чанков: порядок и ссылку на конкретную строку
  каждого чанка (`ChunkId` + версия строки), например в таблице
  `BusinessEntityChunkReferences (BusinessEntityId, Version, Position, ChunkId,
  ChunkRowVersion)`. Чтение версии N идёт строго по её списку. Вставка или удаление
  чанка в новой версии не меняют старые версии.
- Каждая версия хранит автора и время сохранения. Список версий показывает автора.
- **Восстановить версию** (следствие Р-10, минимальная функция): команда во вкладке
  «Версии» создаёт новую версию, равную выбранной (ссылки на те же строки чанков,
  тот же manifest, автор — восстановивший). Существующие версии не удаляются
  и не меняются.
- ReplaceRichTextChunksAsync не стирает все версии. Удаление стартового
  чанка при импорте не уничтожает данные прежнего снимка.
- Старые ссылки на вложения остаются читаемыми. Изменение указателя публикации
  не переписывает содержимое опубликованной версии.
- Эта задача исправляет механизм записи и чтения истории и добавляет только
  «Восстановить версию» (см. выше). Усечение истории и новые правила
  автоматической чистки не добавляются.

### 3.10. Dirty и сохранение рабочего экземпляра миниаппа

Рабочий экземпляр имеет явный контекст сохранения: EditSessionId, MiniAppId,
LogicalWindowId, ContextId и владельца-пользователя. Набор редактируемых сущностей
может быть больше одной. UI-компоненты одного экземпляра используют это состояние
совместно; два окна имеют независимые контексты.

Общая механика в Core/Infrastructure предоставляет регистрацию участника,
dirty/clean, SaveAsync, DiscardAsync, получение фактического исхода операции
и уведомление об изменении состояния. Состав пакета и предметные проверки
реализует миниапп. Сохранение не требует размножения одинаковых хелперов.

При Save фиксируется снимок отправленных правок. Успех очищает только этот
снимок; правки, добавленные во время Save, остаются dirty. Ошибка сохраняет
черновик и dirty. Повторный Save одного экземпляра не запускает параллельно
два применения одного снимка.

Discard удаляет локальные несохранённые изменения контекста и перечитывает
сохранённое состояние. Он не откатывает уже принятые транзакции других окон.
Закрытие одного вспомогательного компонента не уничтожает общий черновик
работающего экземпляра миниаппа.

Переход со страницы, смена пространства и другие действия, завершающие
контекст, проходят Save/Discard/Cancel. Ошибка Save или Cancel оставляет
страницу и правки на месте. Закрытие окна использует beforeunload;
браузер показывает стандартное предупреждение. Автовосстановление черновика
после аварии браузера/процесса в эту задачу не входит.

Dirty пространства и DataProvider не отслеживается. Реестр открытых dirty
контекстов окна нужен для навигации; он не создаёт глобального Save.


### 3.11. Без наследия (Р-16)

Цель — чистая архитектура, а не плавный переход. Поэтому:

1. **Схема БД** создаётся новым кодом с нуля. Сырой SQL `ALTER TABLE ...
   ADD COLUMN IF NOT EXISTS`, `ADD CONSTRAINT`, `DO $$ ... $$`-backfill для старых
   баз удаляются. Остаётся только `CREATE` актуальной схемы. Версия схемы хранится
   в метаданных; несовпадение — явная ошибка запуска, а не тихая миграция.
2. **Данные** не мигрируются и не «чинятся» на старте. Порядок при несовместимости
   схемы — §0.2 п. 4.
3. **Старые API** не оборачиваются. Метод, заменённый новым контрактом, удаляется,
   все вызовы переводятся в том же пакете работ. Временный адаптер допустим только
   внутри одного пакета и удаляется до его завершения. В конце этапа устаревших
   публичных методов нет.
4. **Поля и имена «для старого кода»** удаляются. Если у поля есть реальная роль,
   она описывается явно и поле переименовывается под неё.
5. **Форматы:** payload читается только из актуального конверта
   `{schemaVersion, kind, payload}`; бэкап — только в новом формате с версией
   формата в манифесте. Старый или неизвестный формат — явная ошибка
   с понятным сообщением, без «по умолчанию».
6. **Клиентский код:** старые алиасы и «запасные» ветки для старой разметки
   удаляются вместе с серверной частью.
7. Комментарии в коде вида «совместимое», «для старого кода», «legacy»,
   «backwards-compatible» после этапа 9 не встречаются. Кроме случаев, когда
   речь о внешнем ограничении (браузер, Authentik); такие случаи пояснены.

**Найденное наследие в текущем коде (удалить; этап — в скобках):**

| Где | Что | Что сделать |
|---|---|---|

## 7. Закрытые вопросы и риски реализации

### 7.1. Повторно не спрашивать

Выбор .NET 9, одной шины, логической изоляции в одном проекте, общего Core,
страниц без вкладок, удаления часов/тестовых страниц, последовательного принятия
сохранений и транзакций миниаппа уже сделан. Семантика первой версии статьи
уточнена отдельно и приведена в Р-9.

### 7.2. Риски и меры

| Риск | Мера |
|---|---|
| Ответ чужого scoped-обработчика общей шины | Фильтрация полного адреса до работы, тесты двух пользователей и двух окон |
| User/DataProvider вызывают друг друга для определения текущего пользователя | Серверный контекст автора устанавливается на входе и передаётся явно |
| Последовательные CRUD-вызовы используют разные DbContext | Общий контекст и транзакция на весь пакет |
| Повтор после таймаута создаёт вторую запись | OperationId, выяснение исхода и защита от повторного применения |
| Потеря новых правок при завершении Save | Ревизия отправленного снимка и отдельное текущее состояние |
| Файловая система не участвует в SQL-транзакции | Подготовка неизменяемых файлов, согласованный коммит ссылок и восстановление |
| Кэш возвращает изменяемые общие экземпляры | Копии/неизменяемые проекции и обновление только после коммита |
| История статьи повреждается при импорте | Состав чанков на версию, отсутствие физического стирания прошлых снимков |
| Общий Core превращается в зависимость от внутренностей миниаппов | Явные публичные контракты, архитектурные тесты |
| Перенос Razor ломает JS/CSS/печать | Перенос экранов по одному, сборка клиентского bundle при изменении его исходников |
| ТЗ v1 и старые политики противоречат решениям | Приоритет §2 v2; обновление профильной политики в соответствующем этапе |
| Backlog `Context/Plans/...` в разделе «Решение от 2026-10-27» говорит «транзакций на уровне DataProvider нет» | Отменено решением 2026-10-28 (журнал решений §2.4); в backlog стоит пометка. Действует §3.8 |
| Р-10 — осознанная полумера: поздняя версия заменяет правки параллельного автора | Принято пользователем. Защита — полная история с авторами и «Восстановить версию». Слияние и уведомления — вне объёма до отдельного решения |
| Core обрастает знанием о конкретных типах | К-1: реестр описателей типов от владельцев, архитектурный тест |
| Регрессия доступа | Матрица anonymous/read/edit/admin, серверные проверки и два пользователя |
| Несовместимая схема и старая БД | Без миграций (Р-16). Один раз спросить пользователя: пересоздать БД/storage или поднять новую пустую БД рядом; volumes без согласия не удалять |
| Наследие «на всякий случай» переживает этап | §3.11; CHK-32 в аудите каждого этапа |

Новые продуктовые вопросы выносятся пользователю. Технические детали,
не меняющие согласованное поведение, решаются исполнителем и фиксируются
в реестрах/политиках в том же изменении.
