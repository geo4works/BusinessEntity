## 0. Поручение и объём

Наполнить External API возможностями существующих владельцев: пространства,
папки и дерево, обычные документы/заметки, большие статьи, изображения, видео
и настройки. Предусмотреть создание, чтение, изменение и удаление там, где эти
операции имеют смысл, а также историю, публикацию и загрузку большого содержимого.

Пользователь поручил подготовить ТЗ для другой модели. Код по этому документу
сейчас не меняется. Будущий исполнитель читает весь комплект и контекст репозитория,
проверяет фактическую структуру и выполняет этапы последовательно.

Главное правило: **ExternalApiMiniApp не реализует собственную бизнес-логику CRUD.**
Он предоставляет HTTP-маршруты и вызывает типизированные capabilities миниаппов.
Общая реализация сценария используется API и UI. Только DataProvider записывает
канонический граф/файлы; User сохраняет своё явно предусмотренное служебное storage.

## 2. Подключение возможностей

Каждый владелец добавляет ToolsetDefinition, capabilities, public typed DTO и
Request/Response, обработчик и Registration binding согласно части 2.
Публичные бизнес-DTO не содержат Razor/viewport UI state, EF DTO, raw SQL,
IServiceProvider, IBrowserFile, произвольный путь сервера или callbacks.

```text
REST endpoint → зарегистрированный typed binding → общая шина
    → владелец операции → проверка прав + подготовка одного пакета
    → публичный DataProvider connector → общая шина → commit/outcome
```

Если сценарий сейчас живёт в Razor или UI working set, выделить его в сервис
владельца. UI использует его напрямую, внешний typed handler — тот же сервис.
Состояние редактора и обработка пользовательского ввода остаются в UI working set;
API не открывает модули страниц и не нажимает декларативные кнопки.

Folder/структурные операции — Tree, тело/название/история документа — его владелец,
Space — Spaces. Общие графовые алгоритмы используются через Core descriptors.
Не вводить общий endpoint «записать любую EntityType по произвольному payload».
Владелец операции может собрать изменения нескольких связанных сущностей;
сохранение этого набора — одна транзакция, не цикл независимых Save.

## 3. Общий контракт CRUD

- Все endpoints находятся в `/api/v1`, требуют Bearer и ApiSession из части 2.
- Каждый ресурс имеет постоянный ID; SpaceId/ParentId задаются явно и проверяются.
- Списки ограничены постраничной выдачей/opaque cursor, с устойчивым порядком;
  права применяются до формирования страниц, counts и cursor.
- Автор и даты записи устанавливаются сервером из проверенного контекста.
- JSON полей не предоставляет права изменить CreatedBy, AuthorUserId, UserId,
  PublishedVersion или техническую версию обходом соответствующей операции.
- Изменения используют Idempotency-Key/OperationId. Состав запроса и сгенерированные
  идентичности фиксируются до повторяемого применения; потеря ответа не дублирует объекты.
- Для версионных сущностей результат включает EntityId, сохранённый Version,
  CreatedVersion и OperationId. Объект возвращается в согласованном состоянии commit.
- Read отдаёт только представление, разрешённое субъекту: draft/history требуют
  соответствующих прав, а published читатель не получает скрытый текущий draft.
- Ошибки — единый контракт каркаса; отсутствие права не заменяется пустым
  успешным объектом. Сервер проверяет ресурсы, даже если capability есть в каталоге.

Операция отдельного HTTP-запроса завершается сама или возвращает зарегистрированную
длительную работу. Между запросами не удерживается открытая SQL-транзакция.
Общего Save/dirty пространства и сохранения произвольного глобального набора нет.

## 4. Toolset spaces

| Метод/маршрут | Capability | Поведение |
|---|---|---|
| `GET /spaces` | `spaces.list` | Доступные пространства, pagination |
| `POST /spaces` | `spaces.create` | Создать пространство с заданным именем и разрешёнными настройками |
| `GET /spaces/{id}` | `spaces.read` | Карточка доступного пространства |
| `PATCH /spaces/{id}` | `spaces.update` | Имя/разрешённые метаданные |
| `GET /spaces/{id}/settings` | `spaces.settings.read` | Настройки пространства |
| `PATCH /spaces/{id}/settings` | `spaces.settings.update` | Типизированные настройки, проверка AdminSpace |
| `POST /spaces/{id}/deletion-plan` | `spaces.deletion-plan` | Проверенный состав будущего удаления и внешние зависимости |
| `DELETE /spaces/{id}?planId=...` | `spaces.delete` | Выполнить подтверждённый актуальный план |

Все маршруты таблиц относительны `/api/v1`.
Создание требует действующих полномочий создания пространства (в текущей модели —
GlobalAdmin); владение OAuth клиентом их не заменяет. Имя и defaults валидирует Spaces.
Создание карточки, обязательных данных и свойств атомарно; no-op не создаёт историю Space.

Удаление сохраняет существующую модель удаления подграфа и защиты внешних ссылок,
не вводит корзину/soft delete. План удаления — техническое подтверждение состава,
а не версия пространства. Он привязан к субъекту/цели, короткому сроку и снимку
состава/зависимостей; изменившийся состав требует нового плана. API не удаляет
всю БД, чужие пространства, Docker volumes или корень storage.

## 5. Toolset tree / folders

Обязательные capabilities: `tree.children`, `folders.create`, `folders.read`,
`folders.update`, `tree.move`, `tree.deletion-plan`, `tree.delete`.

Предлагаемые routes:

- `GET /spaces/{spaceId}/tree?parentId=...&cursor=...` — ограниченный список детей;
- `POST /spaces/{spaceId}/folders`, `GET/PATCH /folders/{id}`;
- `POST /tree/move` — явный набор EntityIds и TargetParentId;
- `POST /tree/deletion-plan`, `POST /tree/delete` — проверенный набор и PlanId.

Создание включает Folder и Contains в одном пакете. Проверяются существование
родителя, принадлежность пространству, допустимый тип, имя, циклы и права.
Перемещение набора целиком либо применяется, либо откатывается. Авторизация
проверяется и на источниках, и на новом родителе. В первой реализации поддержать
перемещение внутри одного пространства; перенос между пространствами требует
отдельно описанной семантики прав/ссылок и в текущем контракте отвергается явно.

Типоспецифичное переименование статьи делегируется её владельцу и создаёт версию
по общей политике, а не меняет только карточку в обход payload. Пустая папка
удаляется штатно; непустой набор требует явного плана с полным составом.
Внешние сохранённые зависимости возвращают конфликт, не повреждаются обходным SQL.
API не использует текущее выделение дерева и Reveal-команды как CRUD.

## 6. Toolset documents

Базовые routes: `POST /spaces/{spaceId}/documents`, `GET/PUT/DELETE /documents/{id}`,
`GET /documents/{id}/versions`, `GET /documents/{id}/versions/{version}`,
`POST /documents/{id}/restore-version`.

- Create принимает ParentId, Title и Content. Карточка, v1 и связь создаются одним Save.
- Read возвращает разрешённый снимок и его Version, а не смешение полей разных версий.
- Update принимает BaseVersion и полный снимок автора — Title/Content, а также
  допускаемые метаданные. Неизвестная база — ошибка; существующая старая база допустима.
- Изменение Title/Content создаёт новую версию; no-op и разрешённые метаданные
  описания версии сами по себе номер не увеличивают.
- Restore создаёт новую версию выбранного снимка, не редактирует историю.
- Delete использует тот же проверяемый механизм зависимостей/удаления владельца.

Не заменять согласованную политику параллельных авторов обязательным `If-Match`
или отказом на любую устаревшую BaseVersion. A и B от v1 сохраняются последовательно;
v3 B содержит состояние B от v1, без примеси v2 A. DTO обязан явно передавать базу.

Для «заметок» сначала согласовать §11. Не объявлять Notes API реализованным только
путём переименования класса/URL без явной договорённости о его семантике.

## 7. Toolset rich-documents

### 7.1. Карточка, содержимое и история

Обязательные группы маршрутов:

- создание/карточка/удаление: `/spaces/{spaceId}/rich-documents`, `/rich-documents/{id}`;
- чтение содержимого: `/rich-documents/{id}/content?version=...&cursor=...`;
- сохранение: `POST /rich-documents/{id}/revisions`;
- список/чтение версий, описание версии, `/publication`, `/restore-version`;
- чтение оглавления и поиск средствами владельца, если включены в каталог.

Внешний формат отделить от EF/storage manifest и UI viewport DTO. Зафиксировать
версионированную схему блоков/HTML-операций и разрешённых ссылок на вложения.
GET частей возвращает явный номер снимка; cursor следующих частей закреплён за
этим снимком. Параллельное сохранение не должно подмешать новый кусок в старое чтение.

Save несёт BaseVersion, название, полный порядок автора и его изменения относительно
базы. Допустимы replace/append/insert/delete на уровне документированной модели,
но append должен иметь определённую базу и воспроизводимый результат при retry.
Клиенту не требуется вычислять физические версии строк чанков. Их согласует владелец
и DataProvider. Старые точные ссылки ChunkId + ChunkRowVersion сохраняются.

Первая успешная запись создаёт v1. Последующие изменения контента/названия — следующую
версию. Publication выбирает существующий снимок и находится вне истории. Restore
создаёт новый снимок. Ограничения чтения published/draft/history применяются отдельно.

### 7.2. Изображения и вставка текста

Через UploadId клиент передаёт изображение в staging, затем команда владельца
включает его в сохранение статьи. Вставка текста/HTML и ссылка на изображение
валидируются владельцем; HTML не исполняет произвольные scripts и ссылки не дают
доступ к серверным путям или произвольному скачиванию сервером внешнего URL.

Сохранение с вложениями гарантирует наличие файлов до публикации ссылок в БД.
Если интерфейс выдаёт предварительный AttachmentId, он означает подготовленный
объект, а не успешно сохранённую версию статьи. Вызов завершения с тем же
OperationId не создаёт повторных файлов/версий. Удаление изображения из нового
снимка не уничтожает файл, используемый старыми версиями.

### 7.3. Импорт книг

Операция импорта принимает завершённый UploadId, целевую статью/родителя,
формат, явный режим Create/Replace/Append и для существующей статьи BaseVersion.
Работа выполняется фоновым runtime владельца; возвращается устойчивый JobId/OperationId.

Первый предлагаемый набор — текущие TXT/Markdown/HTML. Один входной документ
создаёт/изменяет одну RichTextDocument; технические чанки не являются главами.
Авторазбиение на отдельные статьи, DOCX/EPUB/PDF и OCR требуют решений §11.
Неподдержанный формат даёт 415, не «успешную» пустую статью.

Разделить транспортную загрузку файла, преобразование содержимого и финальный
Save. Запись каждой сетевой части не создаёт версию статьи. Create даёт одну v1
после готовности; Replace/Append — одну версию результата. Промежуточная статья
не выдаётся за завершённый импорт; при необходимости технический job хранится отдельно.

## 8. Toolset media / uploads / jobs

### 8.1. Общий транспорт загрузок

Общие механизмы загрузки находятся в Infrastructure/DataProvider, а назначение
файла и правила — у RichText/Media владельца. External API принимает bytes и
связывает их с server-issued UploadId; не выбирает canonical путь и не пишет
готовые файлы в папки сущностей самостоятельно.

Предлагаемый протокол:

1. `POST /uploads` — назначение capability/владелец, длина, формат, optional digest;
   сервер проверяет допуск, квоту и выдаёт UploadId/размер частей/срок.
2. `PUT /uploads/{id}/parts/{partNumber}` — ограниченный поток части, offset/length/hash.
3. `GET /uploads/{id}` — принятые части/прогресс; позволяет продолжить после обрыва.
4. `POST /uploads/{id}/complete` — проверка полноты и digest; перевод в Ready.
5. Предметная команда `rich-documents.import` / `media.create` использует Ready UploadId.
6. `DELETE /uploads/{id}` — отмена неиспользованной загрузки; cleanup только её staging.

Повтор идентичной части идемпотентен, другой контент по тому же номеру — конфликт.
Не принимать произвольные offset за границами, upload другого автора, чужое
назначение или истёкший UploadId. UploadId не даёт доступа без identity/session.
Состояние частей устойчиво к рестарту. Файл хранится потоком на диске, не в
общей шине или массиве размером с загрузку. Непрозрачные staging references
разрешает сервер; клиентский путь никогда не передаётся как доверенный temporary path.

### 8.2. Видео

Обязательны список/карточка/создание из UploadId/изменение разрешённых metadata/
удаление MediaVideo и чтение разрешённых bytes с Range. SpaceId явный;
автор/допуск проверяются владельцем. Thumbnail/transcoding предоставляются только
если действительно поддержаны, а не заглушкой «обрабатывается».

Вставка видео в статью использует согласованный идентификатор/ссылку владельца;
перенос/удаление учитывает действующие ссылки и версии. Изменение metadata видео
не создаёт историю статьи само по себе. API jobs доступны только разрешённому
субъекту; текущий общий UI-список очереди не копируется как публичный endpoint.

### 8.3. Длительные работы и память

Job хранит owner, LocalUserId/client, целевой контекст, вход, BaseVersion,
OperationId, ограничения допуска, состояние и результат. Техническое физическое
хранение обеспечивает DataProvider; предметные состояния определяет владелец.
Новый прямой DbContext для External API/Media/Import не добавляется.

Состояния: Queued / Running / Succeeded / Failed / Cancelled / NeedsReauthorization;
неизвестный исход commit сверяется с DataProvider, не считается Failed автоматически.
После рестарта работа продолжается безопасно либо получает достоверное состояние
с возможностью повторить зафиксированный пакет. Долгая работа не держит HTTP scope,
cookie или ссылку на Razor component.

Перед финальной записью проверяются актуальные права. Изменение IdP/epoch или
отзыв допуска не превращает job в System: непринятые к commit работы приостанавливаются
для повторного разрешения тем же LocalUserId; уже принятый commit учитывается по outcome.
Отмена после commit возвращает факт завершения, а не обещает откат.

Существующий импорт с MemoryStream/ToArray нужно переработать для крупных входов.
Ограниченные сетевые буферы недостаточны, если parser/формирование EntitySaveBatch
затем держат несколько полных копий книги. Разрешено расширить общий технический
протокол подготовки/применения чанков через доверенный staging manifest, сохранив
один финальный атомарный Save, полную версию автора и строгие storage contracts.
Не вводить обход транзакций ради загрузки частями.

Измерить end-to-end память/время и зафиксировать поддержанные пределы. Предлагаемый
инженерный минимум smoke: текстовый импорт 100 MiB и потоковая загрузка видео 1 GiB;
это ориентир для проверки, не обещание поддержки произвольного размера. Точный
пользовательский предел/форматы уточняются до этапа крупных импортов (§11).

## 9. Настройки и границы дополнительного объёма

`settings` публикует отдельные типизированные capabilities:

- системные параметры приложения от SysParametersMiniApp — чтение/изменение GlobalAdmin;
- параметры пространства от SpacesMiniApp — по правам данного пространства;
- персональные настройки от UserMiniApp — своего LocalUserId.

Разрешены только явно перечисленные поля/операции. «Произвольный ключ config»,
строка подключения, путь storage, JWT signing key или secret провайдера не становятся
обычным редактируемым параметром. API управления провайдерами, ролями, пользователями
и назначениями не входит автоматически в «настройки»: это отдельное расширение
User toolset после согласования, страница провайдеров уже реализована частью 1.

Комментарии можно экспонировать существующими create/read от Activity. По текущей
comments-policy edit/delete не реализованы и не должны появляться как фиктивный
CRUD. Реакции/лайки/новые типы заметок/каталогов/сущностей также не добавляются молча.

Новые API downloads проверяют права и не перенаправляют клиента на старую публичную
ссылку как способ «авторизованного» чтения. При этом закрытие **всех прежних** HTTP
ссылок остаётся отдельной [TASK_SECURITY_001](TASK_SECURITY_001_file-download-authorization.md).
Наличие проверки в API v1 не позволяет заявить, что прежние URL уже защищены.
Если приёмка потребует полной приватности файлов всей установки, сначала согласовать
включение этой отдельной задачи, не отмечать её выполненной в данном пакете.

## 10. Этапы и приёмка

| Этап | Объём | Проверка результата |
|---|---|---|
| 0 | Сверка кода после частей 1–2; точные schemas/capabilities/routes, решение открытых вопросов затронутого этапа | Есть матрица владельцев и прав; нет дублирующего CRUD |
| 1 | Spaces, Folder/tree, базовый Document | Без UI создать Space → Folder → Document, read/update/delete, retry |
| 2 | RichText CRUD, состав версии, история, публикация/restore | Два автора, старые чанки, published/draft, no-op |
| 3 | Upload staging, картинки, MediaVideo CRUD/Range | Обрыв/возобновление/restart/неверный digest/чужая загрузка |
| 4 | Крупные импорты и durable jobs | Книга/видео целевого размера, restart, отмена, один commit |
| 5 | Разрешённые настройки, согласованные дополнительные операции | Разные области прав, сохранение набора, неизменность секретов |
| 6 | Регрессия UI/API/провайдеров, каталог и документация | Полный внешний сценарий и инварианты архитектуры |

Часть 1 вводится один раз на новой пустой БД. Завершение очередной части/этапа
не разрешает сбрасывать уже созданные данные ради удобства тестов. Нужные схемы
всего комплекта проектируются перед первым вводом; при новой несовместимости
исполнитель сообщает её и не выполняет скрытый reset/миграцию.

Обязательные сценарии:

- CRUD-01: скрипт без cookie и UI проходит вход, сессию, Space/Folder/Document CRUD.
- CRUD-02: один и тот же Idempotency-Key после потери ответа/restart не создаёт второй объект, файл или версию.
- CRUD-03: другой запрос с тем же ключом даёт конфликт; другая identity не читает чужой outcome.
- CRUD-04: нельзя записать в чужое пространство подменой SpaceId/ParentId, скачать draft через published endpoint или получить его через поиск/оглавление.
- CRUD-05: список, cursor и counts не раскрывают скрытые объекты; большие деревья не требуют выгрузки всего графа клиенту.
- CRUD-06: A/B от v1 дают независимые полные v2/v3; restore v2 даёт v4; publication не переписывает историю.
- CRUD-07: технические части загрузки не создают версий; незавершённый импорт не объявляется готовой статьёй.
- CRUD-08: ошибка при сохранении связанных объектов откатывает пакет целиком; файлы восстанавливают согласованность по manifest.
- CRUD-09: insert/delete чанков и вложений сохраняет чтение старых версий.
- CRUD-10: конфликт внешних ссылок и изменившийся deletion plan отклоняются, не обходятся SQL.
- CRUD-11: два параллельных HTTP-запроса не разделяют черновик, пользователя и текущий SpaceId.
- CRUD-12: готовый UploadId другого пользователя/назначения и изменение повторной части отвергаются.
- CRUD-13: после restart загрузка/длительная операция имеют достоверный прогресс и исход.
- CRUD-14: замер больших файлов подтверждает заявленные размеры/лимиты памяти; RequestSizeLimit сам по себе не считается проверкой.
- CRUD-15: отмена, истёкшая сессия и переключение IdP не дают ложного rollback и не повышают права фоновой работы.
- CRUD-16: новая API-функция и UI используют общий сценарий владельца; архитектурный тест запрещает чужие Internal/DbContext в External API.
- CRUD-17: существующие browser-сценарии редактора, дерева, Save/Discard и двух окон проходят.
- CRUD-18: настройки одной области не позволяют редактировать другую или получить секреты.

Для каждого этапа — build, применимые unit/real-Postgres тесты, RSTT и внешний
HTTP smoke плюс регрессия затронутого UI. В отчёте приводить фактические результаты,
незапущенные сценарии и ограничения. Данные тестов изолированы. Коммит/push —
по отдельному указанию пользователя на этот новый комплект.

## 11. Уточнения пользователя при начале раскатки

Решения получены 2026-10-29 после поручения реализовать комплект:

1. Заметка — существующий Document. Отдельные Note/NotesMiniApp не создаются.
2. Первый импорт: TXT/Markdown/HTML в одну большую RichTextDocument.
   DOCX/EPUB/PDF/OCR и разбиение на статьи-главы в этот пакет не входят.
3. Предел книги — 100 MiB, видео — 1 GiB; одна тяжёлая обработка одновременно.
   Эти величины проверяются end-to-end нагрузочными сценариями.
4. «И прочее» ограничено явно перечисленными существующими сущностями/операциями;
   новый предметный домен потребует отдельного решения.

Технические варианты маршрутов и схем можно уточнять в рамках владельцев и
согласованных правил; изменение версионирования, прав, удаления и предметных
типов требует явного решения, а не молчаливого расширения реализации.
