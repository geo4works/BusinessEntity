Отвязать BusinessEntity от конкретного провайдера учётных записей. Ввести общий
контракт и страницу настройки, позволяющую подключить несколько провайдеров,
проверить их и переключить приложение с одного на другой.

Перед реализацией прочитать [llmstart](../llmstart), [index](../index.md),
[work_process_guide](../work_process_guide.md), [routines](../routines.md),
[rollout-context](../rollout-context.md), профильные политики и все три ТЗ.
Сверить приведённый ниже инвентарь с кодом. Не переносить автоматически статусы,
разрешения на коммиты или очистку данных из TASK_ARCH_001 в новый пакет.

Текущему исполнителю поручена только подготовка документов. Следующая модель
реализует комплект после отдельного поручения пользователя. Настоящий документ
не означает, что код, контейнеры, провайдеры или схема уже изменены.

## 1. Решения пользователя и границы

Подтверждено в разговоре 2026-10-29:

1. Authentik становится одной из подключаемых реализаций.
2. Нужна отдельная страница настроек с переключением, в том числе Authentik A ↔ Authentik B.
3. Поддерживаются собственный Authentik в составе установки и внешний существующий сервер.
4. При переносе локального пользователя, отсутствующего в целевом провайдере,
   создаётся внешняя учётная запись с тем же логином.
5. Совпадение имени с существующей, ещё не связанной учётной записью целевого
   провайдера — ошибка. Автоматического слияния по имени/email нет.
6. Новые человеческие учётные записи получают **индивидуальные временные пароли
   с обязательной сменой при первом входе**. Старые пароли не переносятся.
7. **Первое внедрение — на новой пустой БД.** Миграции существующих данных 0.17.0
   не пишутся. При последующих переключениях провайдера локальные ID, права,
   авторство и пользовательские данные сохраняются.
8. Последующие части — каркас API, затем его предметное наполнение. В этой части
   не реализуются CRUD контента, загрузка книг и внешний HTTP API.

Выбор новой пустой БД не является разрешением удалить существующую БД, Docker
volumes или storage. Для первого внедрения использовать отдельную БД и отдельный
пустой каталог canonical storage; старую установку сохранить. Физическое удаление
старых данных требует отдельного явного указания.

Технические решения §§3–9 задают предлагаемую реализацию этих требований.
Они не объявляются ранее принятыми дословными решениями пользователя.

## 3. Архитектура и владение

### 3.1. Общая граница

```text
OIDC provider (Authentik A / Authentik B / другой OIDC)
       ↓ стандартный протокол, проверенные токены
Infrastructure/Identity — протокол, discovery, ключи, cookie/session integration
       ↓ нейтральная проверенная модель
UserMiniApp — LocalUserId, привязки, профили провайдеров, переключение, права
       ↓ публичные типизированные контракты / общая шина
Остальные миниаппы и будущий ExternalApiMiniApp
```

Общий слой не содержит предметных правил пользователей/ролей. UserMiniApp владеет
ими и страницей управления. Протокольные и vendor-specific реализации изолированы;
другие миниаппы не получают Authentik client, его DTO или сырой ClaimsPrincipal.

Сохранить одну общую шину. UI UserMiniApp вызывает собственные сервисы напрямую;
чужие потребители используют Contracts и шину. Core не начинает зависеть от User.
Оболочка получает страницу и ссылку декларативно, без прямой вставки её компонента.

### 3.2. Контракты и возможности

Имена допустимо уточнить без изменения разделения ответственности:

- `IdentityProviderProfile` — сохранённые параметры подключения и ревизия.
- `VerifiedExternalIdentity` — доверенные ProviderId/Issuer/Subject, тип субъекта,
  отображаемое имя и профильные claims после проверки протокола.
- `IIdentityProtocolAdapter` — OIDC challenge/callback/logout и получение
  проверенной identity; интегрируется со штатными ASP.NET Core handlers.
- `IIdentityProvisioningAdapter` — необязательные поиск/создание пользователя,
  установка временного пароля, требование его смены, получение устойчивой identity.
- `IdentityProviderCapabilities` — явно поддержанные возможности.
- `IIdentityProviderRegistry` — доступ к проверенным версиям профилей и активному выбору.

Не сводить всё к `ValidateLoginPassword()`: такой контракт исключает MFA,
корпоративный SSO и внешние системы без прямого password API. Результат адаптера
имеет стабильную типизированную модель; сменяется реализация его получения.

Минимум: общий OIDC adapter и Authentik provisioning adapter. Для другого OIDC
вход работает без vendor SDK. Автоматическое создание аккаунтов у произвольного
провайдера обещать нельзя: OIDC не стандартизует эту операцию. Нет нужной
capability/доступа — явный отказ соответствующего действия, не фиктивный успех.

### 3.3. Хранение

Профили, внешние привязки, активный выбор, эпоха аутентификации и журнал процесса
переключения — служебные данные UserMiniApp в его собственном storage. Это расширение
существующего исключения User, не право писать бизнес-граф напрямую. Атомарные
пакеты административных изменений использовать через UserOwnedStorageWriter и
транзакцию DataProvider; пароли/токены в пакет и outcome не включать.

Secrets профилей представлены `SecretRef`: ссылки на заранее подготовленные
оператором секреты окружения/смонтированного secret store. В первой версии страница
редактирует ссылки и показывает наличие, но не читает/не возвращает значения.
Разрешаются только объявленные identity-secret references, не произвольное чтение
любых переменных окружения. Полноценный UI-менеджер хранилища секретов вне объёма.

## 4. Модель профиля и пользователя

### 4.1. Профиль подключения

Обязательные поля/смыслы:

- ProviderId — постоянный GUID профиля; DisplayName; AdapterKind.
- Issuer, MetadataAddress, ClientId, ClientSecretRef, разрешённые callback/logout URI.
- Scopes пользовательского входа и явное сопоставление профильных claims.
- ProvisioningAdapterKind, ManagementEndpoint, ManagementSecretRef — если используются.
- Развёртывание: ManagedLocal / External; bootstrap разрешён отдельно.
- Revision; Enabled; результат проверки и проверенная Revision.
- Возможности: интерактивный вход, поиск/создание, обязательная смена пароля;
  M2M capabilities для части 2.
- `ApiTokenProfiles` для части 2: точные доверенные issuer/metadata address,
  API audiences, разрешённые OAuth clients и правила claims. Интерактивное OIDC
  приложение и OAuth ресурс API могут иметь разные регистрации и issuer; доверие
  одному хосту само по себе не разрешает все выпущенные им токены.

Issuer не заменяется внутренним Docker-адресом. При необходимости допускается
явно настроенный back-channel, но проверка issuer/подписи сохраняется. Активный
issuer, subject policy и credentials не редактируются незаметно «на месте»:
новая ревизия проходит проверку и активацию, старые проверки становятся недействительными.

### 4.2. Локальная запись и внешняя привязка

`LocalUser` сохраняет Id, Login, DisplayName, состояние и тип Human / Service /
LocalSystem. Пароли и vendor-specific ID не являются полями общего профиля.

`ExternalIdentityLink` содержит LocalUserId, ProviderId, Issuer, Subject,
внешний account ID адаптера, статус и сведения происхождения связи.

- Проверенная пара `(Issuer, Subject)` не может указывать на два LocalUserId.
- Разные профили с тем же issuer не создают отдельное пространство имён subject.
- Один локальный пользователь может иметь привязки к A и B; возвращение к A
  использует прежнюю связь, а не создаёт новую учётную запись.
- Username/email — атрибуты и ключи поиска конфликта, но не доказательство identity.
- Нельзя считать management PK/UUID/UID автоматически равным OIDC `sub`.
  Адаптер обязан доказуемо получить соответствие для настроенного subject mode.
  Если разные OAuth clients получают разные subjects, связывать их только
  проверенным механизмом адаптера, а не совпадением имени.
- Изменение issuer/subject mapping уже связанного профиля требует нового плана привязок.

Авторство графа, роли, группы, назначения, UserProperties ссылаются на LocalUserId.
Они не переписываются при переключении. LocalSystem (`system-anonymous`, seed и др.)
не переносится во внешний провайдер; Service переносится отдельно от людей и
не получает человеческий временный пароль/интерактивную смену пароля.

## 5. Страница «Провайдеры идентификации»

Маршрут предлагается `/administration/identity-providers`; размещение — Page.
Право — локальный GlobalAdmin, проверяемый на сервере для каждой операции.

Страница содержит:

1. Список профилей: имя, тип, адрес, активен/неактивен, версия и состояние проверки.
2. Создание и редактирование неактивного профиля; настройку SecretRef.
3. «Проверить подключение» — discovery/issuer/ключи/callback и заявленные capabilities.
4. «Пробный вход» — отдельную проверку целевого профиля, не меняющую активный.
5. «Подготовить переключение» — таблицу пользователей: связан / будет создан /
   конфликт / недоступен / не переносится; причины по каждой строке.
6. «Создать недостающие аккаунты» — явную операцию по подготовленному плану.
7. Одноразовую выдачу временных паролей только инициирующему администратору.
8. «Переключить» — активацию готового плана с подтверждением завершения сессий.
9. Журнал попыток, ошибок и текущего шага; возврат к ранее настроенному профилю.

Сохранение настроек не активирует профиль. Активный профиль и использованные
привязки не удаляются. Неактивный неиспользованный черновик можно удалить;
использованный профиль отключается с сохранением аудита. Список профилей можно
иметь любой, но в первой версии **один активный провайдер на установку**.
Выбор отдельного IdP на пользователя/пространство и федерация нескольких активных
провайдеров не входят в объём.

## 6. Сопоставление и создание аккаунтов

| Состояние | Результат |
|---|---|
| Есть локальный пользователь и проверенная связь с целевым аккаунтом | Использовать связь после проверки существования и доступности аккаунта |
| Есть локальный пользователь; связи нет; логин в цели свободен | Создать целевой аккаунт, задать индивидуальный временный пароль, зарегистрировать связь |
| Есть локальный пользователь; связи нет; логин в цели занят | `identity.username_conflict`; план не готов к переключению |
| Связь есть, но внешний аккаунт исчез/заменён/отключён | Явная ошибка; не перепривязывать автоматически к новому владельцу того же имени |
| Внешний пользователь входит впервые, локального нет и логин свободен | Создать локальную запись и связь после проверки входа; автоматических административных прав нет |
| Внешний пользователь входит впервые, локальный логин уже занят другой identity | Явная ошибка, без слияния |
| Нет возможности проверить каталог/создать аккаунт/обеспечить смену пароля | `identity.capability_unavailable`; создание и соответствующее переключение блокируются |

Проверять точные логины с правилами регистра/нормализации целевой системы.
Конфликты выявлять до создания аккаунтов, где возможно; гонку между проверкой
и create обрабатывать тем же явным конфликтом. При конфликте пользователь может
исправить имена или аккаунты во внешней системе и построить новый план. Ручное
слияние уже существующих аккаунтов по кнопке «это тот же человек» в v1 не добавлять.

Созданный данным процессом аккаунт можно повторно использовать только по
достоверно сохранённому внешнему ID/маркеру принадлежности операции. Совпадение
логина после сетевого таймаута само по себе не разрешает присвоить аккаунт.

Новые внешние учётки не становятся администраторами самого Authentik. Полномочия
в BusinessEntity сохраняются локально. Существующие пароли/группы/профили чужих
аккаунтов не сбрасываются и не «чинятся» startup-кодом.

### 6.1. Временные пароли

Генерировать криптографически случайный отдельный пароль каждому Human с учётом
политики провайдера. Смена обязательна **до выдачи рабочей сессии BusinessEntity**.
В Authentik это требует настроенного flow/policy, а не только вызова `set_password`.
Проверка capability должна подтверждать такую конфигурацию реальным сценарием.

Одноразовую выдачу делать по защищённому каналу страницы администратору: значения
не сохранять в логах, истории форм, общем кэше, bus events, DB/outcome или отчёте.
Автоматическая отправка писем в объём не входит. При утрате результата допускается
явная повторная выдача нового временного пароля только созданному этим планом
аккаунту, ещё не завершившему первый вход; старый пароль становится недействительным.
Для уже активированного аккаунта — штатный recovery провайдера.

## 7. Процесс переключения и отказоустойчивость

### 7.1. Подготовка

План фиксирует OperationId, исходный/целевой профили и их Revision, текущую AuthEpoch,
снимок локальных пользователей, инициатора и результаты сопоставления. Сохраняется
служебный журнал шагов без секретов. Только один процесс активации одновременно;
конкурирующий план получает конфликт актуальности.

Состояния: Draft → Validated → Provisioning → Ready → Activating → Active;
Failed/Cancelled/NeedsReconciliation содержат причины и известные внешние эффекты.
Ошибка любого обязательного пользователя блокирует активацию всего плана.
Изменение локального состава/целевого профиля делает прежнюю проверку неактуальной.

Создание аккаунтов у IdP — внешний эффект. SQL rollback не удаляет эти аккаунты.
После частичного сбоя старый профиль остаётся активным; повтор продолжает процесс
по журналу без дублей. Неизвестный результат create сверяется с внешним сервером.
Автоматически удалять подготовленные аккаунты при отмене запрещено.

### 7.2. Защита доступа администратора

Перед активацией нужен успешный пробный вход в целевой профиль под учёткой,
доказуемо связанной с локальным GlobalAdmin. Если её только создали, при пробном
входе выполняется смена временного пароля. Это ограниченная проверка конкретного
плана, а не полноценный параллельный вход через неактивный профиль.

Для новой пустой установки предусмотреть документированный одноразовый bootstrap:
конфигурация начального профиля и привязка первого администратора по проверенному
внешнему subject/подтверждённому provisioning. Само имя `admin`/`akadmin` не даёт
прав. Начальные секреты задаются/генерируются установкой, фиксированных паролей нет.
После завершения bootstrap повторный старт не создаёт администраторов заново.

### 7.3. Активация

1. Повторно проверить план, права инициатора и доступность целевого профиля.
2. Закрыть приём новых изменений приложения на короткое время переключения;
   дождаться завершения уже принятых записей. При таймауте активацию не выполнять.
3. В одной локальной SQL-транзакции сменить ActiveProviderId, увеличить AuthEpoch
   и зафиксировать результат операции. Подготовленные связи уже достоверны.
4. Переключить runtime-конфигурацию на committed revision и снять блокировку.
5. Завершить старые cookie/API-сессии; следующий вход выполняется через новый IdP.

Нельзя объявить активацию завершённой, пока старый контекст может начать новую
запись. Общий механизм admission/drain применяется и к UI, и к будущему API;
не превращает DataProvider в владельца правил конкретного провайдера.
Внешние эффекты, уже начатые ранее, учитываются журналом, а не объявляются отменёнными.

При рестарте единственный источник активного выбора — БД, не память или env
«по умолчанию». Сбой после commit распознаётся как завершённая активация по outcome.
Автоматического fallback на старый/случайный провайдер при недоступности нового нет.

Возврат B → A — новая проверяемая активация с новой AuthEpoch. Старые отозванные
сессии от возврата не оживают. Подготовить операторскую процедуру восстановления
доступа при недоступном IdP: локальная административная команда на хосте с явным
выбором известного профиля, новым epoch и аудитом; не анонимный HTTP bypass.

### 7.4. Сессии и черновики

Cookie содержит локальный UserId, ProviderId и AuthEpoch. Проверка выполняется
при запросах и при действиях живого Blazor circuit, а не только при новом login.
Старый callback/refresh после смены профиля отклоняется. Профиль и revision
прикрепляются к начатому login flow; код от A нельзя завершить как вход через B.

Перед переключением UI явно сообщает о завершении активных сессий и риске потери
несохранённых локальных черновиков. Инициатор проходит существующий dirty guard.
Чужие черновики не сохраняются автоматически. Их долговременное восстановление
по-прежнему вне объёма; нельзя обещать бесшовный перенос открытых редакторов.

## 8. Вход и режимы развёртывания

- Использовать штатный OIDC Authorization Code + PKCE, проверку state/nonce,
  подписи, issuer, audience, срока токенов, callback и доверенного redirect.
- Разбор JWT без проверки не является аутентификацией. Не генерировать случайный
  subject при отсутствии обязательного идентификатора.
- Общая страница входа предлагает вход через активный профиль с его названием.
  Прямое воспроизведение Authentik password-flow не является обязательным контрактом
  и удаляется из общего пути; MFA и смену пароля обслуживает провайдер.
- Нормализованный пользователь и права доступны остальным через UserMiniApp.
  Vendor group names могут отображаться в профиле, но не назначают GlobalAdmin
  автоматически; в этой версии административные назначения локальные.
- ManagedLocal поднимает Authentik и может однократно подготовить OIDC/provisioning.
- External не поднимает Authentik/его БД и не зависит от их контейнеров. Для самого
  входа management token не обязателен. Без него создание отсутствующих аккаунтов
  недоступно, а переключение возможно только при уже подтверждённых привязках.
- Новый профиль не требует пересборки приложения. Добавление неизвестного
  нестандартного протокола требует адаптера; произвольная система «по одному URL»
  не считается автоматически поддержанной. SAML/LDAP напрямую в v1 не входят.

## 9. Этапы реализации

| Этап | Результат | Проверка |
|---|---|---|
| 0 | Аудит кода; новые модели, контракт и план новой пустой установки | Сверены точки Authentik coupling; старые данные не затронуты |
| 1 | Схема профилей/привязок/User, bootstrap, OIDC adapter | Реальный вход и локальная identity; неверные токены отвергаются |
| 2 | Страница профилей, проверки и пробный вход | Права, декларативный host, правка не активирует профиль |
| 3 | Authentik provisioning, временные пароли и журнал | Конфликты, смена пароля, retry после частичного сбоя |
| 4 | Активация/возврат, epoch, drain, recovery | A → B → A, сохранность UserId/авторства/прав, старые сессии отвергнуты |
| 5 | External deployment, общий OIDC и документация | Без локального Authentik; вход через другой OIDC test provider |

На этапе 0 спроектировать целевую служебную схему всего комплекта: профили,
привязки, процессы переключения, API grants/sessions и технические operation
receipts. Их DDL включить в создание новой схемы, чтобы части 2–3 не требовали
повторного сброса уже созданных данных. Зарезервированные таблицы не означают,
что соответствующие API/сценарии реализованы; это явно отмечается в отчёте.

После этапа с кодом: build решения, применимые unit/SQL/integration тесты, RSTT
по routines, browser smoke затронутых UI-сценариев и отчёт фактических результатов.
Тестовые провайдеры и БД изолировать от действующих. Не засчитывать mock adapter
как проверку настоящего OIDC или обязательной смены пароля.

## 10. Приёмка

- AUTH-01: два независимых Authentik A/B настроены на странице без изменения кода.
- AUTH-02: A → B → A сохраняет локальные ID, авторство документов, роли и UserProperties.
- AUTH-03: незанятое имя создаёт ровно один целевой аккаунт; повтор не дублирует его.
- AUTH-04: занятое имя без прежней связи блокирует план, пароль/группы существующего аккаунта не меняются.
- AUTH-05: временные пароли различны; первый вход требует смены; до смены нет рабочей сессии.
- AUTH-06: потеря HTTP-ответа create и перезапуск процесса не приводят к присвоению чужой учётки.
- AUTH-07: сбой до активации оставляет A активным; сбой после SQL commit восстанавливает B.
- AUTH-08: старые cookie/callback/circuit и, после части 2, API session не допускаются после смены epoch.
- AUTH-09: две одновременные активации не расходятся; stale plan отклоняется.
- AUTH-10: read-only профиль без provisioning не выдаёт ложный успех создания.
- AUTH-11: не-GlobalAdmin не может изменить профиль/прочитать секрет/активировать план.
- AUTH-12: имя `akadmin` у другого issuer не даёт административных полномочий.
- AUTH-13: logout/login и обязательная смена пароля работают через штатный OIDC flow.
- AUTH-14: профиль и связи переживают restart; значения секретов отсутствуют в БД, логах и bus contracts.
- AUTH-15: режим External запускается без локальных контейнеров Authentik.
- AUTH-16: новый generic OIDC fixture с реальными подписанными токенами работает без Authentik DTO/ветвей.
- AUTH-17: процедура восстановления доступа проверена; постоянного обхода входа не появилось.
- AUTH-18: первая новая установка не изменяет/не удаляет исходную БД и storage 0.17.0.

## 11. Документация и передача

Обновить users/admin-users policies: их нынешние требования об обязательном
Authentik, именах администраторов и фиксированных паролях заменяются этим ТЗ
при реализации. Обновить index, rollout-context, Deployment и реестры сообщений,
модулей/маршрутов. Удалить заменённые Authentik-only контракты и обработчики;
не оставлять совместимые фасады старой identity-модели.

Отчёт: этап, сделано, отклонения, фактически запущенные проверки/результаты,
незапущенные проверки, затронутые БД/провайдеры, текущие ограничения, версия/commit
только если они действительно изменены. Коммит/push — по отдельной команде
пользователя для этого нового комплекта; старое разрешение CMMTP для ARCH_001
не является автоматической командой для AUTH_001.
