## 0. Назначение и границы

Создать ExternalApiMiniApp — внешнюю программную точку входа в BusinessEntity.
Клиент должен пройти аутентификацию, открыть сессию, получить сведения о себе
и доступных возможностях, вызвать объявленный типизированный сценарий и закрыть
сессию. Каркас должен позволять подключать операции владельцев без копирования CRUD.

Пользователь разделил работу на три части: сменяемая identity, каркас API,
затем CRUD пространств/дерева/документов/статей и других сущностей. В этой части
не реализуются предметный CRUD, импорт книг и загрузка видео. Для проверки
полного пути нужен один реальный безопасный сценарий `user.self.read` от UserMiniApp.
Синтетические изменяющие capabilities допустимы только в тестовой сборке.

Подготовка этого документа не разрешает начать реализацию. Будущий исполнитель
читает llmstart, профильные политики и весь комплект; правила новой пустой установки,
коммитов, проверок и запрета очистки данных — [часть 1, §§0–1, 9–11](TASK_AUTH_001_pluggable-identity-providers.md).

## 2. Границы компонентов

### 2.1. ExternalApiMiniApp

Владеет внешним контрактом, версией `/api/v1`, преобразованием DTO, каталогом
экспонированных capabilities, HTTP endpoints, их жизненным циклом и диагностикой.
Исполнение чужого сценария — только типизированным запросом через общую шину.

Не получает чужие Internal/Facade/Storage, DbContext, BusinessEntityHelper для
универсального обхода владельцев, IServiceProvider для поиска произвольного
сервиса или публичный endpoint прямого `EntitySaveBatch`/SQL/graph write.

### 2.2. Общая инфраструктура

`Infrastructure/Identity` из части 1 проверяет протокол и доверие к провайдеру.
`Infrastructure/Api` предоставляет транспортные механизмы: policy, route binding,
ошибки, request context, лимиты, OpenAPI и типизированные binding primitives.
Здесь нет правил публикации, создания папок и версий статей.

### 2.3. UserMiniApp и предметные владельцы

UserMiniApp владеет локальной identity, служебными субъектами, разрешёнными
интеграциями, сессиями безопасности и проверкой прав. Его служебная схема/Writer
хранит записи этих сущностей по существующему исключению User. External API не
создаёт собственный SQL-контекст с копией пользователей/ролей/сессий.

Предметный миниапп объявляет capability и реализует операцию. Его собственный UI
и обработчик API-команды используют один внутренний сценарий владельца напрямую.
Конкретный новый UI не обязан отправлять запрос самому себе через шину.

## 3. Аутентификация клиента

### 3.1. Получение токена

Главный первый сценарий — программа/скрипт со служебной учётной записью.
Программа получает OAuth access token у активного провайдера, затем обращается
в BusinessEntity. Для Authentik использовать поддержанный M2M flow с отдельными
служебными credentials; обычный пароль человека не является универсальным API-login.

Нейтральный внешний контракт принимает `Authorization: Bearer <access_token>`.
BusinessEntity в этом пакете не становится собственным OAuth token issuer и
не выдаёт бессрочный «master API key». ID token и cookie не заменяют access token.
Конкретные credentials и token endpoint описываются в инструкции клиента для
активного профиля; протокол получения может отличаться у другого провайдера.

Для Authentik приёмка включает реально полученный токен технического аккаунта,
а не только JWT, самостоятельно подписанный тестом. При необходимости клиент
создаётся оператором в IdP; общий API не требует права управлять внешним каталогом.

Допускаются делегированные access tokens человека от разрешённого OAuth клиента,
полученные через code flow/PKCE. Не добавлять обмен обычного логина/пароля человека
на локальный токен BusinessEntity. Если профиль не поддерживает M2M, это явно
отражается в capabilities; машинный вход не имитируется человеческим cookie.

### 3.2. Проверка и ограничения

Обязательно проверять подпись/разрешённый алгоритм, issuer, API audience,
срок действия и тип токена согласно контракту доверенного профиля. Разрешённые
OAuth clients и способ чтения client identity заданы серверной конфигурацией;
параметр `clientId` из тела запроса не предоставляет полномочий.

Использовать только `ApiTokenProfiles` активного провайдера из части 1. Если
интерактивная регистрация и API-ресурс имеют разные issuer/subjects, это явно
настраивается и проходит проверку связей; нельзя принимать токен только потому,
что его issuer расположен на том же сервере Authentik. Новый token profile
активируется с изменением security revision/epoch, а не расширяет доверие молча.

После проверки UserMiniApp находит связанную локальную Human/Service identity.
Для API необходим отдельный локальный допуск интеграции (`ApiAccessGrant`):
разрешённый субъект, клиент, ограничения capabilities/пространств и состояние.
По умолчанию допуска нет. Название служебной учётки не даёт GlobalAdmin/IsSystem.
Материализация identity сама по себе не включает доступ к API.

Для первоначальной настройки расширить административный UI UserMiniApp:
GlobalAdmin выбирает проверенную локальную Service/Human identity, разрешённый
OAuth client и ограничения API, сохраняет/отзывает допуск. Связывание внешней
служебной учётки проходит проверенный механизм части 1; совпадение имени не
обходит её правила конфликта. Документировать получение service credentials
у провайдера. Настройка не должна требовать ручного INSERT в БД или отправки
секретов в обычной форме выдачи прав; identity adapter отвечает за их отдельную
одноразовую выдачу, если такая возможность включена.

Фактическое право — пересечение проверенных ограничений токена, локального
допуска интеграции, ограничений сессии и текущих предметных прав пользователя.
Изменение/отзыв локального допуска проверяется на последующих запросах, даже если
подписанный JWT ещё действителен. Отсутствие scope claim не трактуется как «всё
разрешено»: профиль явно определяет соответствующий контракт API scope/claims.

## 4. API-сессия

### 4.1. Смысл и данные

ApiSession — серверная запись контекста интеграции, а не Blazor circuit, окно,
открытый редактор, транзакция БД или глобальный dirty/save-контекст.

Сессия содержит: SessionId, LocalUserId, ProviderId, AuthEpoch, проверенную
идентичность OAuth client, ссылку/ревизию допуска интеграции, суженные ограничения,
CreatedAt, ExpiresAt, состояние Active/Revoked/Expired и технический аудит.
Токен, пароль и refresh token в записи сессии не сохраняются.

Предлагаемый начальный абсолютный срок сессии — 1 час, задаётся конфигурацией.
Сессия не продлевает JWT: каждый запрос обязан нести действующий access token.
После обновления токена у IdP клиент может продолжить ту же неистёкшую сессию,
если проверенные субъект, профиль/epoch и OAuth client совпадают. Иначе новая сессия.

### 4.2. HTTP-контракт каркаса

| Метод и маршрут | Назначение | Условия |
|---|---|---|
| `POST /api/v1/sessions` | Открыть сессию; вернуть SessionId, срок и разрешённые ограничения | Валидный Bearer + действующий ApiAccessGrant |
| `GET /api/v1/sessions/current` | Прочитать свою текущую сессию | Bearer + `X-BE-Session-Id` |
| `DELETE /api/v1/sessions/current` | Закрыть свою сессию | Те же identity/client; повтор безопасен |
| `GET /api/v1/me` | Выполнить `user.self.read`, вернуть безопасную локальную карточку | Bearer + активная сессия |
| `GET /api/v1/capabilities` | Доступный данному клиенту каталог, версии и схемы | Bearer + активная сессия |
| `GET /api/v1/operations/{operationId}` | Достоверный статус своей принятой операции | Bearer + сессия; серверная проверка принадлежности |

SessionId не является credential. Зная его без токена соответствующего субъекта
и клиента, нельзя выполнить запрос. Для истёкшей/отозванной сессии ответ — 401
с кодом причины; для живой identity без права — 403. Повтор DELETE уже закрытой
собственной сессии допускается с действующим токеном и возвращает 204.

Каталог отражает общий допуск capability, а не гарантирует право на любой EntityId.
Каждый ресурс проверяется дополнительно при вызове. Сессия не содержит выбранное
в браузере пространство; SpaceId/ContextId передаются явно в предметном запросе.

### 4.3. Завершение и смена провайдера

Сессии хранятся устойчиво и после рестарта остаются действующими только в пределах
своего срока/допуска/epoch. Смена провайдера или security revision из AUTH_001
делает старые API-сессии недействительными; возврат к A их не оживляет.

Закрытие сессии запрещает новые вызовы, но не откатывает уже принятую запись.
Принятая длительная операция имеет отдельный OperationId; её исход может быть
прочитан после повторного входа тем же локальным субъектом при соответствующих
правах. Переключение IdP использует admission/drain части 1. Повторный токен не
продлевает сессию автоматически и не повышает её исходные ограничения.

## 5. Execution context и шина

Каждый HTTP-запрос создаёт отдельный DI/request scope, даже внутри одной ApiSession.
Установить доверенный LocalUserId из проверки токена/сессии; не принимать его,
IsSystem или административный флаг из клиентских JSON/headers.

Различать:

- ApiSessionId — продолжительная сессия интеграции;
- ScopeId — конкретное выполнение запроса;
- RequestId — корреляция сообщения;
- OperationId — устойчивый ID изменения/повтора;
- ContextId/SpaceId — явно заданный предметный адрес;
- AuthEpoch и проверенный client/grant context — ограничения безопасности.

Для HTTP нет пользовательского LogicalWindowId/ModuleId. Уточнить текущий
BusRequestContext так, чтобы API/background адрес не маскировался под окно.
Scoped endpoint фильтрует свой execution scope до чтения состояния, UI endpoints
не исполняются из API без настоящего живого UI binding. Изменение контракта
перевести во всех местах сразу, без второго транспорта и старых wrapper-ов.

Два параллельных запроса одной сессии не делят mutable state, текущего автора,
выбранное пространство или рабочий набор. Освобождение HTTP scope не должно
уничтожать принятую долговременную операцию; её runtime принадлежит владельцу.

## 6. Toolset-ы и публикация операций

### 6.1. Рекомендуемая модель

Использовать [существующую политику](../Policy/MiniApps/capability-toolsets-policy.md).
Toolset — именованный набор возможностей владельца, а не комплект новых CRUD
реализаций внутри External API. Это не MCP server и не требование внедрять AI tooling.

Владелец регистрирует:

- ToolsetId/Version, CapabilityId/Version, OwnerMiniAppId, название/описание;
- типизированные вход/выход и публичные schema identifiers;
- HTTP method/route и правила binding;
- признак Read/Write, нужный контекст, требования допуска и предметных прав;
- правила идемпотентности, выполнения/ожидания и получения исхода;
- ограничения размера и поддержанные форматы при необходимости.

Декларации собираются инфраструктурой через типизированные GiveMe/HereAre сообщения
на общей шине; в эксплуатации каталог зафиксирован при старте. Новые владельцы
подключаются регистрацией и перезапуском; горячая загрузка кода не требуется.
Дубликаты capability/route/schema и отсутствие binding — ошибки запуска.

### 6.2. Типизированное исполнение

REST JSON десериализуется на границе в известный тип входа зарегистрированного
binding. Локальный generic adapter отправляет конкретный `TRequest` через
BusRequestClient и принимает конкретный `TResponse`. В шину не попадает
универсальный конверт `{ string Type; object Payload; }` или произвольный JSON
как исполняемая команда. Metadata/schema может описывать формат, но не подменяет
типизированный runtime contract.

Binding объявляется владельцем через общую инфраструктуру в Registration.
ExternalApiMiniApp не вызывает Registration чужих миниаппов — это делает
композиционный корень. Он не вызывает чужой внутренний сервис по reflection,
delegate или имени метода. В payload нет DbContext, Stream, IBrowserFile или
пути файловой системы. Транспорт файлов в части 3 использует отдельный механизм
загрузки и непрозрачный server-issued UploadId.

Обязательный реальный toolset каркаса — `user`, capability `user.self.read`.
Его предметный результат выдаёт UserMiniApp; External API не разбирает claims
заново. Возвращать LocalUserId, тип, имя и состояние; не сырые claims/токены/секреты.
Предметные CRUD toolset-ы подключаются только в части 3.

## 7. Ошибки, повтор и контракт эксплуатации

### 7.1. HTTP-ошибки

Единый JSON ProblemDetails со стабильными Code, RequestId, при наличии OperationId.
Не возвращать stack trace, SQL, секреты или содержимое чувствительных входов.

| HTTP | Пример |
|---|---|
| 400 | Неверный DTO, обязательное поле, недопустимый параметр |
| 401 | Нет/неверен/истёк токен, сессия недействительна, сменился провайдер |
| 403 | Действующая identity не имеет права на capability/ресурс |
| 404 | Нет доступного ресурса/операции; не раскрывать чужие идентификаторы |
| 409 | Конфликт idempotency key или технической ревизии настройки |
| 413 / 415 | Превышен размер / неподдержанный формат |
| 429 | Лимит запросов/параллельных выполнений; Retry-After |
| 503 | Недоступна обязательная зависимость; исход записи не объявляется откатом |

API не перенаправляет на HTML login/space-selection. Для неизвестного исхода
записи возвращать OperationId и явное состояние Unknown/Pending с адресом
проверки; 202 допускается только если операция действительно зарегистрирована
и существует механизм её отслеживания. Timeout не равен Cancelled/RolledBack.

### 7.2. Идемпотентность

Задать общий контракт для изменяющих capabilities: `Idempotency-Key` и
серверный OperationId, семантический hash типизированного запроса, identity/client/
capability/version. Повтор с другим содержимым даёт 409; с тем же — тот же результат.
Секреты исключаются из receipts, запросы аутентификации не пишутся туда целиком.

Особенно учесть создание: повтор после утраченного ответа не должен заново
генерировать EntityId/ChunkId и попадать в конфликт собственного пакета.
Сопоставление ключа с зафиксированным запросом, выделенными идентичностями и
результатом должно переживать restart. Outcome и business commit связаны одной
транзакцией DataProvider. Pending registration может предшествовать ей, но не
считается подтверждением commit и после сбоя требует reconciliation.

Техническое хранение operation receipts/подготовленных пакетов канонических
операций принадлежит DataProvider, не SQL-репозиторию ExternalApiMiniApp.
Это расширение технического механизма OperationId, а не новый доменный CRUD.
Срок гарантированного повтора явный и согласован с retention outcome (сейчас 7 дней);
после него нельзя обещать exactly-once. Получение исхода ограничено автором/клиентом
и не требует сохранения прежнего SessionId.

В этой части проверить механизм на тестовом владельце/пакете без добавления
производственных тестовых endpoints. Полный путь реального создания сущности
обязательно проверить при первом этапе CRUD части 3.

### 7.3. Эксплуатация

OpenAPI v1 описывает реальные routes, Bearer, session header, DTO, ошибки,
идемпотентность и примеры. Внешние DTO не равны storage DTO. Лимиты запросов,
размера JSON, времени ожидания и конкурентности конфигурируются; HTTP только
для явно ограниченного локального dev, рабочее развёртывание через HTTPS.

Не включать CORS `*` с credentials. Cookie-интерфейс остаётся отдельной схемой;
его старые маршруты не объявляются новым API v1. Логировать actor/client/session/
operation/capability/result без Authorization, password, refresh token и тел файлов.
Минимальный клиентский пример должен получать настоящий токен, открывать сессию,
вызывать me/catalog и завершать сессию без cookie/браузера.

| Этап | Результат | Приёмка |
|---|---|---|
| 0 | Аудит после AUTH_001; точные DTO/identity/token profile | Нет нового Authentik coupling или второго token issuer |
| 1 | Bearer policy, служебная identity, ApiAccessGrant | Разрешённый/запрещённый клиент, scope, audience, срок |
| 2 | ApiSession и отдельный request execution context | Open/read/close/restart; параллельные запросы, смена IdP |
| 3 | Toolset catalog/bindings, `user.self.read`, OpenAPI | Реальный bus-вызов; дубликаты/неизвестное явно отвергаются |
| 4 | Общие ошибки, повторы, лимиты, аудит | Потеря ответа/restart/параллельный retry на тестовом владельце |
| 5 | Интеграционный smoke, документация и передача части 3 | Клиент без UI проходит весь цикл с Authentik A и B |

## 9. Проверки приёмки

- API-F01: новый миниапп зарегистрирован в существующем каталоге; шина одна.
- API-F02: настоящий M2M токен открывает сессию; ID token, cookie-only, неверные issuer/audience/signature — нет.
- API-F03: без локального допуска интеграция не получает API-доступ, даже с валидным JWT.
- API-F04: SessionId без токена и с токеном другого субъекта/клиента бесполезен.
- API-F05: refresh токена той же identity не продлевает абсолютный срок сессии.
- API-F06: закрытие, блокировка субъекта/допуска и смена AuthEpoch прекращают новые вызовы.
- API-F07: два клиента/две сессии/параллельные запросы не смешивают авторство и ContextId.
- API-F08: API не зависит от cookie выбранного пространства, Razor renderer и открытого редактора.
- API-F09: `me` проходит через типизированный User contract; raw claims и секреты не возвращаются.
- API-F10: нельзя выполнить незарегистрированную capability или передать имя CLR-типа/метода для выполнения.
- API-F11: каталог и OpenAPI соответствуют зарегистрированным endpoints; дубликаты останавливают запуск.
- API-F12: runtime не получает object-конверты, EF DTO или чужие внутренние сервисы.
- API-F13: потеря ответа и retry не создают дубль; другой payload с тем же ключом отвергается.
- API-F14: операции/сессии после restart имеют достоверное состояние; Unknown не объявляется rollback.
- API-F15: 401/403 — JSON, без redirect; лимиты дают предсказуемые ошибки.
- API-F16: сценарий работает при внешнем Authentik без его локальных контейнеров.
- API-F17: после A → B запросы с A/sessionA отвергаются; новая сессия B работает.
- API-F18: production routes содержат только каркас и `user.self.read`, без тестовых probes и предметных CRUD заглушек.

Сборка, unit/SQL/auth integration, RSTT и smoke обязательны для изменённого кода;
browser smoke проверяет, что обычный вход и UI не сломаны. Тестирование выполняется
на отдельных БД/identity fixtures, не сбрасывает действующее пользовательское хранилище.

## 10. Документация и передача

Обновить реестры миниаппов, модулей, сообщений и capability-toolsets policy;
создать каталог API capabilities с владельцами и стабильными ID. Обновить index,
deployment/identity настройки, инструкцию клиента и smoke. Старые публичные
контракты при замене удаляются вместе с вызовами, без временной совместимости.

При завершении приложить реальные результаты тестов, список доступных маршрутов,
известные ограничения и доказательство вызова через шину. Полный CRUD не объявлять
выполненным в этой части. Коммит/push — по отдельному указанию пользователя.
