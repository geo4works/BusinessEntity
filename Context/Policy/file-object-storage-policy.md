# Постоянные файлы BusinessEntity

Canonical файлы пишет и удаляет только DataProvider. MediaServer может владеть
временной очередью загрузок; backup может писать внешние архивы из временных
экспортных копий. Логи, входящие временные файлы и restore reports не являются
canonical payload сущностей.

Storage:RootPath задаётся явно и является внешним bind mount. В текущем стеке
это `BusinessEntityStorage` репозитория → `/app/storage`. Storage:HostRootPath
используется только для отображения и перевода пути настроек backup.

## Идентичность и запись

Логический ключ файла: EntityId + FileId + Variant. Bytes, имя и MIME по уже
существующему ключу неизменяемы. Для замены нужен новый FileId.

```text
{StorageRoot}/business-entities/{EntityId}/objects/{SHA256}.blob
{StorageRoot}/.staging/{OperationId}/{temporary}.tmp
```

DataProvider фиксирует содержимое входа и SHA256. Большое видео передаётся
временным серверным путём и копируется потоком; byte[] на весь файл не требуется.
Временный путь не входит в идентичность операции; digest и длина входят.

До SQL-коммита bytes полностью записываются в staging, проверяются, публикуются
atomic move. SQL-пакет содержит карточки, payload, связи и manifest файлов.
HTTP получает путь только из проверенной проекции DataProvider. До коммита
метаданных новый файл по логическому адресу не виден.

## История и восстановление согласованности

Политика типа объявляет зависимости каждой версии от файлов. Новая версия
проверяет существование файлов перед commit. SQL FK защищает постоянный файл,
пока на него ссылается хотя бы один сохранённый снимок. Удаление видео, которое
используется историей другой статьи, отклоняется всем пакетом.

При удалении подграфа сначала удаляются его исходящие исторические зависимости;
ссылки из оставшегося графа продолжают защищать свои файлы. Физическое удаление
неиспользуемых объектов выполняется после commit.

Recovery запускается до runtime и после завершения записи под writer gate.
Сначала читается достоверный manifest БД. Недоступная БД не является основанием
для удаления файлов. Убираются только не referenced `objects/*.blob` и staging;
архивы backup не затрагиваются. Ошибка уборки логируется, не меняя уже принятый
исход SQL-транзакции; следующая recovery повторяет работу.

Ни ссылки на ещё не записанные bytes, ни перезапись bytes под историческим ID
не допускаются. Файлы и все исторические ссылки входят в полный backup/restore.

## Проверки

Интеграционные тесты проверяют отказ до file publish, отказ SQL commit, сироты
после прерывания, неизменяемость идентичности, потоковый временный источник,
защиту файлов историей и восстановление полного подграфа. SQL-транзакция и
файловая система проверяются отдельно.
