# Хранение RichTextDocument в чанках

Актуализировано на этапе 2 TASK_ARCH_001 v2.2. Имя файла сохранено как адрес
политики; действуют точные составы версий, атомарный пакет и неизменяемые файлы.
Обратной совместимости схем, JSON и API нет.

## Модель и владельцы

RichTextDocument — самостоятельная сущность и страница. Её manifest содержит
настройки формата, а тело находится в технических строках чанков. Чанк не
является отдельной BusinessEntity графа. Пространство не имеет общей версии.

Владелец домена — RichTextDocumentMiniApp. Он объявляет ownership, правила
версий, файловых зависимостей и перепривязки архива. Общий алгоритм транзакции
находится в DataProvider. Перенос компонентов и helper к владельцу завершается
на этапе 6; наличие registrations не означает завершения этого переноса.

Core предоставляет общие модели и алгоритмы. Знание конкретных доменных типов
заменяется описателями владельцев по К-1; предметные HTML-правила не дублируются
в общем движке.

## Canonical payload

JSON envelope содержит schemaVersion, kind, createdByUserId,
lastModifiedByUserId и object payload. Все обязательные поля присутствуют;
неизвестные поля, kind и schemaVersion дают явный отказ.

Manifest kind=RichTextDocument. В payload находятся tag, contentStorage,
editorFormat, chunkPolicy, embeddedFileStorage и supportsImages. Текущий формат:

- contentStorage: ChunkedBlocks;
- editorFormat: BlockJsonWithInlineHtml;
- chunkPolicy: RichTextMvpV1;
- embeddedFileStorage: LocalDocumentFiles.

Имена, номера, авторы и время версии — metadata строки payload. ID payload
равен ID сущности. PublishedVersion хранится в карточке и только проецируется
в runtime manifest; внутри JSON истории указателя публикации нет.

Пустой текст и пустой список блоков допустимы. Отсутствующие поля, null вместо
обязательного поля, повреждённый JSON и неизвестный формат не превращаются
в пустую статью или значение по умолчанию.

## Строки чанков и состав версии

BusinessEntityDataChunks имеет PK (Id, Version), BusinessEntityId, SortOrder,
Data, PlainText, HtmlCache, BlockCount, CharCount, DataSizeBytes и Checksum.
Строка конкретного чанка неизменяема после принятия снимка.

BusinessEntityChunkReferences имеет EntityId, Version, Position, ChunkId и
ChunkRowVersion. Каждый элемент версии ссылается на конкретную существующую
строку; порядок берётся из Position reference, а не SortOrder прежней строки.
На уровне SQL действуют внешние ключи и уникальность позиции и ChunkId в версии.

Чтение «последнего чанка с Version <= N» запрещено: оно смешивало бы правки
разных авторов и возвращало удалённые из снимка чанки.

## Блоки

Data чанка — envelope kind=RichTextDocumentChunk с payload.blocks[]. Текущая
runtime-модель RichTextBlock содержит обязательные поля kind, level, html,
imageId, displayVariant, altText, width, height, videoId, videoTitle. Поля,
не используемые данным kind, имеют явно сериализованное пустое/нулевое значение.

Поддерживаются paragraph, heading, code, list, image, video и table. Неизвестный
kind и null-элемент отклоняются. HTML не является моделью всего документа:
он хранится внутри отдельных блоков.

- Paragraph и heading содержат inline HTML; heading задаёт уровень заголовка.
- Code и list содержат HTML своего блока; таблица — HTML таблицы.
- Standalone image ссылается на локальные ImageId и DisplayVariant, содержит
  altText и размеры. Изображение в абзаце может быть inline marker с
  data-rich-image-id. Standalone image — поддерживаемый текущий блок.
- Video ссылается на ID MediaVideo; inline вариант использует
  data-rich-video-id. Это ссылка на сущность, а не абсолютный файловый путь.

Правила таблиц и редактора дополняют эту политику:
[таблицы](Tables/rich-doc-tables-policy.md),
[Tiptap/ProseMirror](Tiptap-ProseMirror-Integration-Guide.md),
[чтение](rich-doc-read-policy.md), [редактор](rich-doc-editor-policy.md).
При расхождении storage/истории действуют настоящая политика и
[правила версий](../business-entity-versioning-policy.md).

PlainText, HtmlCache, размеры и статистика — производные значения. Канонический
источник — blocks JSON. HTML cache строится с ID текущего документа и чанка;
при restore производные значения пересчитываются для новых идентичностей.
Оглавление строится из блоков точной выбранной версии.

## Сохранение полного состояния автора

Создание карточки, manifest v1, стартового состава и Contains-связи происходит
одним EntitySaveBatch. Save существующей статьи содержит BaseVersion автора,
полный manifest и название, изменённые чанки и при необходимости полный ChunkOrder.
Если ChunkOrder=null, используется порядок BaseVersion. Неизменённые чанки
берутся только из конкретных references BaseVersion.

DataProvider под writer gate назначает следующий номер. Fingerprint включает
название, предметное содержимое и упорядоченные ChunkId + Checksum. Изменение
контента или названия создаёт версию. No-op и изменение описания не увеличивают
номер. Изменение настроек manifest само по себе не считается правкой текста.

Вставка, split, merge и удаление меняют состав новой версии. Прежние строки и
references остаются. Импорт также создаёт полный новый снимок и не удаляет
исторические чанки и файлы. Парсинг, нормализацию и разбиение готовит владелец;
физическая запись принадлежит DataProvider.

При параллельной работе A и B от v1 получаются последовательные v2 и v3;
v3 = v1 + изменения B. Неизменённые B чанки не подхватываются из v2.
Автоматического слияния нет.

Команда «Восстановить версию» создаёт следующий полный снимок выбранной версии
с новым автором и временем. Предыдущие версии не переписываются. Указатель
публикации остаётся выбранным отдельно. Версии показывают название и автора.

## Публикация и чтение

Публикация выбирает существующую версию через отдельное изменение карточки.
Она не увеличивает номер и не меняет ни одного JSON payload истории.
Пользователь с полным доступом может просматривать историю; доступ только к
публикации читает именно PublishedVersion, включая её название и состав.

Чтение больших документов оконное. Сначала загружаются карточка/manifest,
затем окно чанков и оглавление. Запрос конкретных ChunkId или membership
не должен материализовывать весь большой документ. Для статистики и экспорта
допустим последовательный обход окон. Один огромный HTML/JSON всего документа
и огромный DOM не являются моделью чтения или сохранения.

База редактора фиксируется по DocumentVersion начального окна. Подгружаемые
окна используют эту же базу. Общее событие другого окна не перечитывает тело
поверх открытого редактора. Полный dirty/Save/Discard и защита навигации
реализуются этапами 4 и 8, не подменяются номером последней версии БД.

## Файлы и архив

Все постоянные bytes и metadata записывает DataProvider. Логический ключ
EntityId + FileId + Variant неизменяем. Bytes публикуются до SQL-коммита ссылок,
а recovery удаляет не referenced объекты после отказа/рестарта.

Каждый снимок объявляет свои файловые зависимости. Незаписанный файл не может
стать ссылкой сохранённой версии; историческая ссылка защищает файл от удаления.
Картинки принадлежат статье, видео может принадлежать MediaServer.

Полный backup включает все версии, exact references, свойства, комментарии и
файлы. Restore перепривязывает ID всех сущностей и чанков, внутренние URL,
видео и anchors; произвольные GUID текста не заменяются. ImageId сохраняется
как локальный ключ уже нового владельца. JSON, checksum, производные поля и
fingerprint пересчитываются. Весь подграф записывается одним пакетом.

Нормативные детали: [файлы](../file-object-storage-policy.md),
[backup](../BackupRestore/space-backup-policy-entity-folder-layout.md),
[restore](../BackupRestore/space-backup-restore-policy.md).
